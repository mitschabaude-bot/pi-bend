# AgentSession over a faux provider

`tests/agent-session.bend` builds an `AgentSession` (`packages/coding-agent/src/core/agent-session.bend`) over a scripted provider, as upstream's `registerFauxProvider` does: every request pops the next scripted text and answers with a start/text/end event stream. `tests/agent_session_check.py` runs six scenario kinds and asserts on the printed JSON events (the print-mode `toSessionJsonEvent` rendering) and on the session file.

- `persist` prompts once against a file-backed session. The events run `agent_start, turn_start, message_start, message_end` (user), `message_start, message_update…, message_end` (assistant), `turn_end, agent_end` (`willRetry: false`), `agent_settled`; the file holds the header, the user entry and an assistant entry equal to the final `message_end` message, chained by `parentId`; `getLastAssistantText` returns the reply.
- `queue` steers and queues a follow-up before prompting an in-memory session. `queue_update` reports the steering text, then both queues, then empty queues; the steering message joins the first turn (upstream's loop fetches steering messages before the first request), the follow-up starts a second turn after the assistant settles, and the session holds both replies.
- `busy` holds the first request open (the provider reports `started` on a channel and waits for `release`) while the prompt runs in a spawned fiber. Meanwhile `isStreaming` is true, a plain `prompt` is refused with "Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.", `prompt` with `steer` and `followUp` behaviors queue; after release the steering message gets the second turn, the follow-up the third, `queue_update` empties in that order, and the prompt fiber finishes with `isStreaming` false.
- `retry` scripts failures (a response starting with `!` fails with the rest as error message) under a `settings.json` retry policy: a transient error emits `auto_retry_start` (attempt, max attempts, delay, message) after `agent_end` with `willRetry: true`, drops the failed assistant message from the agent's context (the session keeps it), sleeps the backoff and continues the agent; the next successful assistant message emits `auto_retry_end` with `success: true` at its `message_end`; exhausting the budget emits `auto_retry_end` with `success: false` and the final error; disabled retry, non-retryable errors and context overflow do not retry; `abortRetry` from another fiber during the sleep ends with "Retry cancelled" and no further request.
- `compact` runs prompts, then compacts manually (`manual`), compacts and calls `abortCompaction` (`cancel`) or `abort` (`abort`, then prompts again) once the summarizer's first retry backoff starts, queues a follow-up before the prompts (`queued`), or leaves automatic compaction to act (`none`). A scripted `text#N` response reports `N` context tokens and `~text` stops at the length limit. Manual compaction emits `compaction_start`/`compaction_end` with reason `manual`, returns the result also carried by `compaction_end`, persists one `compaction` entry (with the summarizer's usage) keyed to the first kept entry, and rebuilds the context with the `compactionSummary` first; a split turn combines the history and turn-prefix summaries. Summarization requests go through the agent's stream function under the retry policy: transient errors emit `summarization_retry_scheduled`/`summarization_retry_attempt_start` per retry and one `summarization_retry_finished`; non-retryable errors, disabled retry and a length-limited summary fail without a compaction entry. A context-overflow error compacts with `willRetry: true`, drops the failed response from the context and continues; a second overflow reports the recovery failure instead of compacting again. A completed run whose usage crosses `contextWindow - reserveTokens` compacts with reason `threshold` and does not continue; usage below the threshold or disabled compaction leaves the session alone. Within a run, the session's next-turn hook estimates the context before each further assistant response and compacts at the threshold first, so a queued follow-up is answered on the compacted context.
- `mutate` sets the thinking level, the model and the session name. `setThinkingLevel("high")` on a model without reasoning clamps to `off` and emits `thinking_level_changed`; `setModel` records a `model_change` entry; `setSessionName` emits `session_info_changed` and records a `session_info` entry.

## Adaptations

- Upstream opens the streaming window with a waiting tool; the port holds the provider request on a channel gate, since the bash tool and tool-waiting harness are not ported yet. `prompt` returns a `Fail` string where upstream throws.
- Upstream's harness reads `session.messages`; the runner reports entry counts and the last assistant text through the same public accessors (`messages`, `getLastAssistantText`, `sessionOf`).
- Extension hooks (`model_select`, input handlers, extension commands) are not ported; the cases that depend on them stay pending.
- Retry settings are read once when the session is created (upstream reads the settings manager on every decision); the port's settings manager is an immutable value and the session has no settings setter yet.
- Backoff delays beyond the timer's 32-bit millisecond range sleep one millisecond, as Node's timer overflow does. The backoff sleep is cancelled through an abort controller kept in the shared state; `abortRetry` after the sleep has already finished is a no-op.
- `isRetrying`, `abortRetry`, `isCompacting`, `abortCompaction`, `compact` and `abort` (cancel the sleep and compactions, abort the agent, wait for idle) are the public surface. `compact` returns a `Fail` string ("Compaction cancelled" when aborted) where upstream throws.
- Upstream's cancellation tests block in an extension's `session_before_compact` hook; extension hooks are not ported, so the port cancels during the summarizer's retry backoff instead, the path #6647 exercises.
- Compaction runs after a run, before a prompt and before each further assistant response of a run (upstream `_installAgentNextTurnRefresh`, which also refreshes the turn's model, thinking level and tools and chains a hook the agent already had); extension-provided summaries, branch summarization and system-state checkpoints are not ported. Upstream has no coding-agent test of the next-turn compaction; the `queued` scenario is a native check. The chained earlier hook and the model refresh are not exercised yet: the coding agent installs no hook of its own, and no scenario switches models mid-run.
- Since v0.87.1 (466db0fec) the session's canonical projection is authoritative. Every provider request is built from it through the agent's `prepareRequest` hook, chaining a hook the agent already had. A retried error, or an overflow attempt that will be retried, stays in the session history, and a `context_edit` omission appended right after `auto_retry_start` (or before the overflow compaction) removes it from the model context; the omission is announced as `entry_appended`. The compaction decision reads the projection: whether the assistant is still projected, whether a later edit or compaction invalidated its usage, and the projected estimate when the context carries edits. `tests/agent_session_recovery_reference.ts` runs the pinned AgentSession harness on the retry and overflow scenarios; the updated expectations (four entries after a retry, split-turn overflow summary, recovery exhausted on the second overflow) agree with it apart from upstream's leading system message, which the port's harness does not persist. The reference needs pi-mono's gitignored model data hydrated (for example from the published pi-ai 0.87.1 `dist/providers/data`). Upstream matches the assistant to its entry by object identity; the port records the entry ids when it persists the assistant message and its turn's tool results, and for the pre-prompt check uses the last projected assistant entry, which is the same entry because the agent's transcript is the projection. Extension turn boundaries (`turn_end` and `agent_before_settle` drafts and continuation) wait for the extension module.
- The prompt and tool loadout (upstream `_preparePromptAndToolLoadout`): the agent starts without a prompt or tools, as upstream's `createAgentSession` does. Each prompt, and each further turn of a run, makes the runtime's tools the agent's executable tools, and prepends a system message patching the prompt sections the transcript declares when they differ. The loop adds the tool declarations to that message, and the session persists it like any other message. The sections are built once when the runtime is created (resource loader, `before_agent_start` and tool-selection changes are not ported), so after the first prompt of a session the patch is empty. `print_cli_check.py` compares the first prompt's section names and the persisted entries of a resumed session with pi 0.87.1. The test harness declares no sections and no tools.
