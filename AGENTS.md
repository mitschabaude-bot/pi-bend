# Faithful pi port

The user requires a close port of pi-mono's modular libraries, internal main types, public APIs and behavior, including terminal UI and dependencies. A working CLI or matching a few visible behaviors does not satisfy the task. Extensions are native Bend; JavaScript/TypeScript extension compatibility is excluded. Preserve pi’s programming concepts and meaningful behavior using idiomatic, functional Bend, not JavaScript runtime semantics. Do not recreate prototypes, property descriptors, reflective object operations, sparse JS arrays, JS key enumeration, or incidental reference identity. Use immutable values and explicit state transitions; retain effectful synchronization only where concurrency requires it. If a meaningful upstream behavior must change, identify its source/test and discuss it with the user before choosing the change.

Reference: sibling `../pi-mono`, commit `46c9de402`. Preserve the upstream package/module boundaries under `packages/`. Preserve public type, field, function and event names where Bend permits them. Document language-driven changes individually; do not collapse typed models into generic JSON, flatten library layers into the CLI, omit hooks, or replace injectable interfaces with hard-coded implementations.

Complex dependencies must be implemented in pure Bend, without C or JavaScript glue. Add missing primitives to Bend where necessary. The prototype's libcurl and ICU adapters are migration liabilities, not approved dependencies for the finished port. Test-only host-language oracles may validate Bend results, but must not supply production behavior.

The current `src/` executable is a bootstrap prototype. Its networking/authentication checks and live subagent demonstrations are useful evidence for the native runtime, not acceptance evidence for the library port. Do not grow this prototype into a separate approximate architecture. Introduce canonical library modules with upstream tests and migrate the entry points onto those modules.

Port meaningful pi-mono test contracts, preserving test names, relevant edge cases and event ordering. Adapt language-specific assertions to native value semantics; document those adaptations instead of emulating JS or treating every JS implementation detail as a requirement. Keep a source-to-port map in `tests/upstream-inventory.json`. Distinguish pending, partial and fully ported suites. Supplement with differential tests and native tests where runtime differences require them. Never weaken expectations to fit the implementation or mark skipped cases as complete.

Push tested milestones to the authorized public GitHub repository. Never commit authentication, tokens, private sessions, generated binaries or vendor downloads. Keep limitations explicit in the README and parity records.

This project also contributes to Bend and its standard library. Prefer idiomatic functional Bend over literal TypeScript translations. Record every encountered compiler/runtime bug, performance cliff and resource-lifetime problem in `docs/bend-issues.md`. Build missing language/library primitives as project implementation work; track their design, implementation and validation alongside the code rather than treating their absence as an external issue. Investigate causes and seek reduced reproducers; a workaround is not resolution. Distinguish confirmed defects, intended language restrictions, missing facilities and hypotheses. Record versions, evidence, regression commands, local patches and upstream status. Do not distort public APIs or weaken tests merely to hide a toolchain problem.

Bend patches must be minimal and must not regress performance. Before installing a patch, compare correctness and relevant performance against an otherwise identical unpatched baseline. Measure both time and memory for memory-management changes. Keep experiments isolated until the evidence supports adoption; lower memory use alone does not justify slower compilation. Record benchmark scope and uncertainty rather than claiming an unmeasured absence of regressions.

Correctness work now prioritizes generic Bend laws and machine-checked proofs for the pure core. Gregor explicitly authorizes the agent to author honest specifications without waiting for his review. Prefer universally quantified invariants that imply upstream test cases; meaningful boundary laws are welcome, but do not turn arbitrary regression examples into concrete equality laws and claim stronger assurance. Keep laws independent of implementation accidents and never weaken them just to obtain a proof. Track upstream assertions against proved laws, executed tests and remaining gaps. Retain external differential, IO/concurrency integration, compiler and performance tests. Replace redundant unit cases only when a proved law covers their contract. First finish and commit the current DNS work, then pause DNS expansion and establish the law/proof workflow on existing foundations before extending further components.

Trust Bend’s compiler to validate proofs. Do not create or run broken-implementation mutations or negative compiler/proof-gate tests. Focus on meaningful generic laws, their proofs, and complementary runtime, differential, integration and performance checks. Historical mutation records may remain as history; they are not ongoing requirements.
