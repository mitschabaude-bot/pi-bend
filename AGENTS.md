# Faithful pi port

The user requires a close port of pi-mono's modular libraries, internal main types, public APIs and behavior, including terminal UI and dependencies. A working CLI or matching a few visible behaviors does not satisfy the task. Extensions are native Bend; JavaScript/TypeScript extension compatibility is excluded. Preserve pi’s programming concepts and meaningful behavior using idiomatic, functional Bend, not JavaScript runtime semantics. Do not recreate prototypes, property descriptors, reflective object operations, sparse JS arrays, JS key enumeration, or incidental reference identity. Use immutable values and explicit state transitions; retain effectful synchronization only where concurrency requires it. If a meaningful upstream behavior must change, identify its source/test and discuss it with the user before choosing the change.

Reference: sibling `../pi-mono`, pinned by `tests/upstream-inventory.json` and `docs/source-coverage-reviews.json`. Preserve the upstream package/module boundaries under `packages/`. Preserve public type, field, function and event names where Bend permits them. Document language-driven changes individually; do not collapse typed models into generic JSON, flatten library layers into the CLI, omit hooks, or replace injectable interfaces with hard-coded implementations.

Complex dependencies must be implemented in pure Bend, without C or JavaScript glue. Add missing primitives to Bend where necessary. Test-only host-language oracles may validate Bend results, but must not supply production behavior. The CLI and its supporting libraries live under `packages/`.

Port meaningful pi-mono test contracts, preserving test names, relevant edge cases and event ordering. Adapt language-specific assertions to native value semantics; document those adaptations instead of emulating JS or treating every JS implementation detail as a requirement. `tests/upstream-inventory.json` tracks test-suite status, while `docs/source-coverage-reviews.json` records source modules that have actually been reviewed for coverage and faithfulness. An absent source record means unreviewed; `docs/source-coverage.md` describes bounded queries, review states and freshness checks. Distinguish pending, partial and fully ported suites. Supplement with differential tests and native tests where runtime differences require them. Never weaken expectations to fit the implementation or mark skipped cases as complete.

Push tested milestones to the authorized public GitHub repository.

This project also contributes to Bend and its standard library. Prefer idiomatic functional Bend over literal TypeScript translations. Record every encountered compiler/runtime bug, performance cliff and resource-lifetime problem in `docs/bend-issues.md`. Build missing language/library primitives as project implementation work; track their design, implementation and validation alongside the code rather than treating their absence as an external issue. Investigate causes and seek reduced reproducers; a workaround is not resolution. Distinguish confirmed defects, intended language restrictions, missing facilities and hypotheses. Record versions, evidence, regression commands, local patches and upstream status. Do not distort public APIs or weaken tests merely to hide a toolchain problem.

Bend patches must be minimal and must not regress performance. Before installing a patch, compare correctness and relevant performance against an otherwise identical unpatched baseline. Measure both time and memory for memory-management changes. Keep experiments isolated until the evidence supports adoption; lower memory use alone does not justify slower compilation. Record benchmark scope and uncertainty rather than claiming an unmeasured absence of regressions.

For pure core behavior, prefer generic Bend laws and machine-checked proofs that establish substantial invariants. Meaningful boundary laws are welcome, but arbitrary regression examples are not stronger merely because they are written as laws. Keep laws independent of implementation accidents and never weaken them just to obtain a proof. Track upstream assertions against proved laws, executed tests and remaining gaps. Retain external differential, IO/concurrency integration, compiler and performance tests. Replace redundant unit cases only when a proved law covers their contract.

Trust Bend’s compiler to validate proofs. Do not create, retain or run broken-implementation mutations or negative compiler/proof-gate tests. State meaningful laws and prove them, alongside runtime, differential, integration and performance checks.

Preserve pi’s meaningful APIs and dependency functionality with minimal, idiomatic Bend. Choose modules by responsibility and consolidate unnecessary forwarding layers. Validate interactive and request behavior directly. Do not expand diagnostic infrastructure or prove obvious wrapping/formatting equalities. Law counts are not a measure of port completion.

Coordinate through `AGENT-LOG.md` (append-only). Read only the last 30 lines, then use targeted `rg` searches if needed; never load the whole log. Reserve shared paths before editing and record committed handoffs. Keep entries to 1–3 short sentences: ownership, commit/result, next action or blocker. Put detailed evidence in the relevant test output or document, and link it instead of repeating it.
