# Bend issues and standard-library opportunities

This is the living investigation log for problems encountered while building pi-bend. The project is also a contribution to Bend: use idiomatic functional representations, investigate toolchain failures, and develop reusable library facilities. A workaround does not close an issue. High RSS alone does not establish a memory leak. Application inefficiency must be distinguished from a compiler or runtime defect.

Last updated: 2026-09-19. Current local compiler: Bend 2.0.7, Bun 1.4.0, with eight local patches listed in [patches/README.md](../patches/README.md). Automatic updates remain enabled; reproduce against recorded source hashes as well as version strings. No upstream issue/PR submission is recorded for these entries.

## BEND-001 — Native compilation consumes tens of GiB

**Status:** confirmed excessive memory consumption on integration fixtures; cause under investigation. Neither an application-runtime leak nor a compiler leak has been established.

The compiler process (Bun running `bend2/main.ts`, emitting C) reached roughly 58 GB RSS during Responses integration compilation and the host began swapping. These were process observations, not instrumented exact peaks. The generated terminal fixture C was approximately 46 MB. The coding agent was not executing. The terminal tests ultimately passed all 119 scenarios on one/four threads after batching them into groups of 16. This does not establish that batching fixes the cause.

The async-driver fixture, batched into eight cases, showed the same problem. A retry with `bun --smol` completed cases 0–7 on both thread counts, but compilation of cases 8–15 subsequently reached 56,569,320 KiB RSS (53.95 GiB) after 2m54s. That process was terminated to protect the shared host. Low-memory mode is therefore insufficient. The remaining driver cases are not yet verified.

The retained integration reproducer is `build/responses-stream-driver-check-8.bend`, generated by `tests/responses_stream_driver_check.py`. This is not a reduced reproducer. At the time of profiling it depended on uncommitted driver modules; these are now retained in the repository. Use `python3 tests/responses_stream_driver_check.py --generate-only` to recreate the original eight-case batches without compiling them, then invoke the guarded profiler on batch 8. Do not run large compiler experiments concurrently.

Investigation tooling: `scripts/profile-bend.py` copies the installed compiler into an ignored build directory, records compiler/input SHA-256 hashes, instruments loading, validation, dependency discovery, each generated definition and each optimization pass, and imposes an RSS cutoff. It does not patch the installation. The cutoff is sampled every 0.5 seconds and can overshoot; it is not an OS hard memory limit. Logs include process memory, pass number, definition times, segment counts and cache sizes. Generated copies and raw profiles stay outside Git.

```sh
python3 scripts/profile-bend.py tests/static-sum-layout.bend --label static-sum-example --smol --rss-limit-gib 2
python3 scripts/profile-bend.py build/responses-stream-driver-check-8.bend --label responses-example --smol --rss-limit-gib 40
```

Use a new label for each run. The small static-sum baseline completed successfully: four code-generation passes, 41 reachable definitions, 854 compiler probes, 1,127 telescope-cache entries and about 125 MiB RSS at the last recorded pass. Its first polling sample missed the short-lived peak; subsequent tooling also records Linux child peak RSS. This is a profiler smoke check, not a performance baseline for the large program.

Source inspection of `bend2/comp.ts` identifies hypotheses to test: native emission repeats complete passes until ownership/hot/static facts stabilize; `TELES` is a strong `Map` retained across definitions and passes; global `PROBES` retains every created probe without a reset. Other temporary maps are cleared by `memo_gc()` at definition boundaries. None of this alone proves which objects account for the observed memory. Do not clear caches or compiler-variable tables indiscriminately: live terms can depend on them.

Next: use the measurements below to separate pattern-lowering allocation from cache retention, compare bounded/weak cache designs, measure scaling with pattern count/length, then test a narrowly justified patch against native one/four-thread and backend regressions. Keep idiomatic generic library interfaces intact while investigating.

### Investigation results, 2026-09-19

The instrumented large input used 1.01 GiB RSS after loading, 4.84 GiB after validation and 6.81 GiB after dependency discovery. Code generation then added approximately 2,993,963 telescope-cache entries per pass. Pass six ended at 18,536,003 entries and 37.70 GiB RSS; the 40 GiB guard stopped pass seven after 114.84 seconds. The cache stores decompositions of function types; it is a strong map, so garbage collection cannot discard its keys or values while they remain stored.

The largest individual growth was `openai-responses-terminal.mapStopReason`: 632,945 new cache entries per pass. `json-string.escapeCode` added 324,245 per pass. These are short pattern-matching functions, not giant fixture literals. This narrows the investigation to compiler expansion/memoization as well as pass lifetime; it does not establish asymptotic complexity yet.

A standalone reproducer is now retained as [tests/compiler-string-match.bend](../tests/compiler-string-match.bend): six string patterns and one print. It produces approximately 78 KiB of C. Three observed unmodified-cache runs used about 687–786 MiB peak RSS and about 2.5 seconds including the profiler's polling delay. A print-only control used about 82 MiB. Counts are more stable than allocator measurements: the string-match program created 25,177 probes and 158,244 telescope-cache entries over two code-generation passes. Exact memory/timing varies between runs; no statistical benchmark or exponential-growth claim is made.

Controlled experiments on that reduced input:

| Experiment | Live heap after collection, pass 1 / pass 2 | Telescope entries, pass 2 | Interpretation |
| --- | --- | --- | --- |
| Force GC after each pass, original cache lifetime | 196.4 / 257.7 MiB | 158,244 | Cached objects remain reachable. |
| Clear `TELES` at existing `memo_gc` boundaries and force GC after each pass | 135.0 / 140.4 MiB | 11 | Much less live retained state; further compiler allocations still exist. |

The original and experimental compiler emitted byte-identical C for the reduced input; the experimental native binary printed the expected result on one and four threads. This is narrow evidence, not full compiler-patch validation. Clearing the cache without forcing collection still reached the large input's 40 GiB guard after 110.83 seconds: strong-cache retention is not the only contributor to process RSS. The combined large-input experiment is tracked separately below. Neither experiment is applied to the installed compiler.

Experimental switches are explicit: `--clear-teles` changes cache lifetime only in the copied compiler; `--gc-passes` forces Bun collection between passes. The profiler also passes a smoke compilation and an intentional low-cutoff termination check. Peak RSS is obtained for the individual child through Linux `wait4`, avoiding inherited/cumulative child-accounting measurements. The guard still only samples, so allow substantial headroom on shared machines.

The combined large-input experiment **completed all 11 passes in 170.10 seconds, peaking at 10.67 GiB RSS**. After collection, live heap stayed around 2.6 GiB across passes; RSS stayed approximately 9.5–10.5 GiB at those boundaries. This is strong evidence that cache lifetime and delayed collection contribute materially to the original memory cliff. It does not explain all of the remaining 10.67 GiB peak or establish that forced GC is the best permanent fix. A bounded or weak cache and allocation reduction deserve comparison. Global probe accumulation remains a separate lead, not the demonstrated primary cause.

The generated large-fixture C compiled with Clang `-O1`, and all eight integration cases in this batch (cases 8–15) passed on one and four threads. These compare callback ordering, tier resolution/pricing and failures with actual upstream behavior. This validates that batch under the experimental compiler, not all 32 driver cases or the broader compiler regression suite.

Selected raw measurements, compiler/input hashes, phase boundaries and largest cache increases are retained in [the measurement record](bend-issues/2026-09-19-compiler-memory.json). Large-fixture results are exploratory and do not promote the whole async-driver suite or a compiler patch to verified status. The installed compiler remains unchanged.

The isolated BEND-001 candidate is now retained as `patches/experimental/bend-compiler-memory.patch`. All seven existing toolchain regressions, canonical library types, all 32 complete async-driver comparisons and 10 original terminal-event instances pass with it, including their native thread/backend checks. This extends the candidate's evidence; it is still not applied to the installation, is Bun-host-specific, and does not resolve the remaining compilation cost or establish general compiler correctness.

## Open runtime, compiler-limit and diagnostic investigations

**BEND-009 — Dropped channel handles do not reclaim live channel rows.** The runtime foundations currently require owner-directed disposal after aliases and observers retire; see [runtime ownership](../packages/runtime/README.md). This is a resource-lifetime gap with leak risk, distinct from BEND-001. Next investigation: a minimal allocate/drop versus allocate/dispose loop, runtime row counts and steady-state memory, followed by an explicit ownership/reclamation proposal. No automatic-reclamation fix or reduced memory measurement is recorded yet. Preserve callback reentrancy and cancellation safety when designing it.

**BEND-010 — Compiler argument-count limit under large callback captures.** Recorded in [parity history](parity.md): the loop-configuration fixture exceeded the compiler's argument-count limit and was reduced by capturing less live configuration. No compiler change was retained. Exact threshold and a standalone reproducer still need reconstruction. Investigate closure environment lowering before treating fixture reshaping as a lasting solution.

**BEND-011 — Deep generated C requires an increased Clang parser limit.** `scripts/build-pure.sh` uses `-fbracket-depth=2048` because generic record match trees exceed Clang's default 256. This is a code-generation interoperability/performance concern; the flag is a workaround. Measure depth and size versus record/variant shape and reduce a failing program. Do not flatten canonical application types merely to fit generated C.

**BEND-012 — Binding/global-name collisions during module integration.** During terminal-module integration, global helpers named `number`, `signature` and `usage` were renamed after import-context name collisions. A new combined Responses test reproduced the problem in a typed `do` binding: the constrained-sampling fixture has both a global `unchanged` helper and a local `unchanged : ... <- ...` binding. Standalone execution succeeded; importing the same file failed with `expected: def, type or law; observed: :`. Copyable `+name` bindings failed with a quantified-datatype diagnostic.

The typed-do case is now a confirmed compiler defect with reduced fixture `tests/typed-do-shadow.bend` and before/after runner `tests/typed_do_shadow.py`. Cause: `parse_term_do_stmt` parsed the left-hand name as a term before checking for `:`, allowing module namespace resolution to turn a local binding into a global reference; `+name` could fail even earlier while parsing quantified types. The local fix recognizes bare typed binding syntax first and retains the original term path for nonbindings. Effectful/pure/copied/nested bindings and initializer/tail global calls pass standalone/imported on one/four native threads and JS; qualified binding names remain rejected. The seven existing compiler regressions and canonical library types also pass. `patches/bend-typed-do-shadow.patch` is applied locally as the eighth patch. Application bindings were not renamed to hide this failure. Pattern/lambda and other previously observed shadowing cases remain open; this is not a blanket resolution of BEND-012.

### BEND-012 performance audit

The typed-do patch was installed after correctness checks but before performance measurement. That sequencing was inadequate. Future patches must be minimal and pass relevant baseline performance comparisons before installation; memory improvements must be evaluated alongside time.

An initial parsing-only comparison uses otherwise identical Bend 2.0.7 sources with this one patch reversed for the baseline. `scripts/benchmark-typed-do.ts` records two variants with alternating execution order, warmup and 30 batches of 10 parses on Bun 1.4.0. Two independent runs on the shared host produced these patched/baseline median-time ratios:

| Workload | Run 1 | Run 2 |
| --- | --- | --- |
| Base | 1.005 | 0.981 |
| Base plus standalone regression | 1.026 | 1.008 |
| 400 ordinary-action functions | 0.977 | 0.980 |
| 400 typed-binding functions | 0.996 | 0.967 |

These mixed, small timing differences do not establish zero overhead. The standalone regression is slightly slower in both runs; further isolation is needed before attributing that to the patch or calling the patch performance-neutral. Both compiler versions emitted byte-identical 92,513-byte C for `tests/typed-do-shadow.bend`, establishing unchanged generated code for that fixture only. No compiler change was installed during this audit. Other seven patches have not received a comprehensive performance audit. Raw timings, hashes, environment and scope are in [the measurement record](bend-issues/2026-09-19-typed-do-performance.json). The memory experiment remains uninstalled; its successful memory reduction is not proof of acceptable compilation speed.

**BEND-017 — Match scrutinees must follow binder order.** On the locally patched Bend 2.0.7, `def example(left: Bool, right: Bool) -> Bool` with `match right left` and rows `True{} True{}` / `_ _` fails with the diagnostic that a name is a def or consumed binder. Changing only the match order to `left right` succeeds. Inspection of `match_flatten` shows that it walks the binder list in order; reaching `right` consumes the earlier `left` as an available scrutinee. This is a current pattern-lowering restriction, not evidence of global-name shadowing. It surfaced in the UTF-8 encoder helper and was handled by aligning its parameter order with its match order, without a compiler patch or behavior change. A clearer diagnostic or support for permuted scrutinees is a possible language improvement; upstream intent has not been established. This should not be folded into BEND-012's distinct typed-binding defect.

**BEND-018 — Type-checking cliff for recursive searches with repeated byte patterns.** `tests/compiler-repeated-byte-pattern.bend` reduces a stalled line-boundary helper to a recursive list search with `case 10 <> 10 <> _`. On locally patched Bend 2.0.7/Bun 1.4.0 it fails to finish a five-second check. Changing only the second literal to 11 checks in 0.14s; replacing the recursive fallback with `None{}` checks in 0.11s. Repeated 13 and repeated 0 patterns also reach three-second limits, as does retaining the repeated-10 pattern while passing the offset unchanged. A single `13 <> 10 <> 13 <> 10 <> _` pattern checks in 0.24s. Timings are observations on a shared host, not a controlled performance benchmark.

The original combined helper was observed still consuming CPU after 86 seconds at roughly 150 MiB RSS; that process was stopped when its source was superseded. An isolated loader/checker confirms loading completes, and per-definition instrumentation places the delay in checking `findBoundary`. Diagnostic copies with limits on weak-head-normalization calls/steps and alias-cycle detection did not identify the cause within their five-second limits. Nontermination and the exact cause are not proven. Next: obtain a reliable checker profile or finer phase instrumentation, then examine repeated-literal refinement and recursive-call checking. No patch was installed. The production boundary finder now uses a small prefix automaton, verified against the SDK; this is a suitable linear scanner but does not resolve the compiler finding. Reproduce with `timeout 5 bend tests/compiler-repeated-byte-pattern.bend`; this intentionally time-limited investigation is not part of the passing application suite.

**BEND-019 — JS backend stack overflow in large `List.append`.** `tests/compiler-js-list-append.bend` repeatedly doubles a 256-element list and checks that the result is nonempty. With locally patched Bend 2.0.7 and Bun 1.4.0, the native build prints `constructed`; the JS build exits 1 with `bend: memory fault (machine stack overflow?)`. Instrumenting only the generated JS diagnostic handler exposes `RangeError: Maximum call stack size exceeded` with repeated frames in `$List$2e$append$`. Trials constructing 4,096, 8,192, 16,384 and 32,768 elements pass; 65,536 fails on this host. These sizes bound this reproducer's observed cliff, not a universal recursion limit. The native TCP backpressure test had passed with the same list-building strategy before the JS run failed.

The transport test now builds the same 65,536-byte payload with tail-recursive block accumulation and passes both backends. No compiler/stdlib patch was installed. Next investigate whether JS lowering should trampoline recursive library calls or Base should supply a stack-safe append, with correctness and time/memory comparisons before adopting either change. Reproduce with `bend tests/compiler-js-list-append.bend -o build/append.js` followed by `bun build/append.js`; compare a native build separately. The application test workaround does not resolve this standard-library/backend issue.

## Standard-library development opportunities

**BEND-013 — Numeric and wire-format foundations.** Pure Bend modules currently supply two-limb U64/U128 arithmetic, binary64 arithmetic/decimal conversion, JSON parsing/encoding and partial streaming JSON. These are reusable library candidates, not reasons to introduce JavaScript value semantics. Evaluate which belong in Base versus separate packages; retain independent arithmetic and codec conformance tests. Lack of native binary64 operations may also be a performance issue, but no comparative benchmark is recorded here yet.

**BEND-014 — Async library ownership and callback ergonomics.** `Callback`, `Deferred`, cancellation, persistent FIFO and event streams are implemented as typed Bend modules. Affine closures and explicit resource ownership shape their APIs; those language features are not defects merely because TypeScript differs. Investigate reusable standard interfaces, safe disposal, reentrancy and observer cancellation; avoid synchronized cells for ordinary data and do not add unrestricted mutation to imitate JS.

**BEND-015 — HTTP/TLS and remaining system facilities.** Native networking and the provider transport remain unfinished. The bootstrap's libcurl adapter is not the accepted final dependency. Before designing each facility, inspect Bend's current primitives and document the exact missing operation, minimal OS boundary, reusable pure-Bend layer and tests. This entry records project needs, not a verified claim that every such facility is absent from the current release.

Inspection of Bend 2.0.7 confirms TCP listen/accept/connect/send/recv already exist, but send/recv cross a UTF-8 string boundary (`io_cstr`/`io_str` in C, `io_bytes`/`io_text` in JS). Arbitrary TLS records and split byte sequences therefore require byte operations. `File.read_bytes` already establishes `List<&2, U32>` as the byte representation. The isolated `experimental/bend-tcp-bytes.patch` candidate adds corresponding socket byte operations by reusing those existing primitive patterns; it changes no existing text operation or compiler/runtime core. A loopback smoke probe sent and received all 256 byte values on one/four native threads and JS. The candidate is not installed and is not yet accepted; see the additional contract checks and limited performance evidence below. HTTP and TLS protocols remain pure-Bend library work, not part of this primitive patch. Current isolated copy: `build/bend-tcp-bytes-candidate`, launcher `build/bend-tcp-bytes-launcher`; the checked-in patch and probe preserve the experiment independently of those ignored files.

The raw-TCP candidate now also passes `tests/tcp_bytes_contract.py` on one/four native threads and JS: invalid-byte EINVAL without partial prefix writes, empty sends, zero-length reads, reads limited to seven bytes, complete byte reconstruction across short reads, repeated EOF, continued use after validation errors, reset-induced read failure and subsequent typed send failure with socket closure. Reset tests coordinate through a one-byte request/acknowledgment before the server closes with reset. These Linux checks do not establish other-platform coverage, partial-write/backpressure scheduling, cancellation semantics or sustained resource behavior. No primitive code changed for these tests.

An initial controlled build comparison uses identical `main.ts`, `bend.ts`, `comp.ts` and all existing effect files; only the extra Base declarations/new effect files differ. Across 20 alternating-order samples after two warmups per fixture, existing text TCP emits byte-identical C and has median wall time 0.289s baseline / 0.287s candidate (ratio 0.996), median peak RSS 153,780 / 152,816 KiB. The UTF-8 runner also emits identical C, with median 1.078s / 1.086s (ratio 1.007), RSS 416,578 / 414,434 KiB. These are loading/checking/C-emission measurements including fresh Bun startup, not Clang or socket throughput. Small mixed differences on a shared host are inconclusive about tiny overhead. Identical generated C establishes unchanged native code only for the measured fixtures. [Raw samples and hashes](bend-issues/2026-09-19-tcp-bytes-performance.json) and `scripts/benchmark-tcp-bytes.py` retain the evidence. The candidate remains uninstalled; the later backpressure results below extend this evidence, while sustained-use and runtime performance checks remain pending.

Backpressure coverage now passes on one/four native threads and JS via `tests/tcp_bytes_backpressure.py build/bend-tcp-bytes-candidate`. This Linux test copies the candidate, sizes kernel buffers only in that copy, and traces scheduler/primitive waits. The peer waits for Bend's initial scheduler read wait before supplying a byte and waits for a real kernel send EAGAIN before draining the 65,536-byte payload; all bytes arrive in order without loss/duplication. A separately injected read EAGAIN checks the retry callback because normal `IO_READ` operations already wait for readability before entering `recv`. Acknowledgment, EOF and closure complete successfully. No sleep guesses readiness. Instrumentation is discarded with the temporary copy; the installed compiler and candidate sources are unchanged. These checks establish read-wait/retry and partial-write resumption, not sustained resource behavior or throughput neutrality. The candidate remains uninstalled.

**BEND-016 — Large native C output and downstream compilation cost.** A combined fixture containing 14 original Responses/constrained-sampling cases and 32 driver comparisons generated 155.35 MiB (162,896,682 bytes) of C. The separate driver fixture previously generated 45.41 MiB, constrained sampling 77.17 MiB and Responses conversion 20.49 MiB. These older artifacts are not controlled same-revision scaling benchmarks. The combined Bend build used the eight local correctness/primitive patches plus the isolated memory experiment; Clang `-O1` was still compiling after 2m51s, at about 2.1 GiB observed RSS. This is distinct from the compiler-cache retention measurements in BEND-001. Next: identify the largest emitted definitions/specializations, compare generated size with source and type shapes, and separate unavoidable specialization from duplicated emission or inlining. Do not simplify canonical application types or weaken assertions to conceal this cost. Final native test results and timing belong to the corresponding validation record; output size alone does not establish a memory leak or asymptotic complexity.

The combined native build subsequently completed and passed all 14 original cases plus 32 driver comparisons on one/four threads. A scan of emitted `WL_CASE` spans identifies `responses-initial-input.finalMessage` at 24.56 MiB, `openai-responses-terminal.incomplete` at 17.09 MiB, `openai-responses-terminal.mapStopReason` at 16.87 MiB and `constrained-sampling.functionMatches` at 14.10 MiB. These spans do not account for the entire C file or separately emitted helpers. The short source functions use nested variants/string patterns; investigate that lowering and indentation before attributing the whole size to fixture count or generic specialization.

### BEND-016 reduction: long string patterns and excessive indentation (2026-09-19)

The new top-level wire decoder initially expanded its string-discriminator match into a 304,242,028-byte generated segment, out of 329,986,385 bytes total. The segment has 197,271 lines and a maximum line length of 2,612 bytes. Inspection shows each character being unpacked into 32 bit tests and then deeply nested conditional branches. The smaller standalone reproducer `tests/compiler-long-string-patterns.bend` has only 16 event-name cases returning integers, yet emits 268,124,850 bytes in 14.32 seconds with `/usr/bin/time` peak RSS 5,623,696 KiB. Of that C output, 262,945,324 bytes (98%) are leading indentation spaces; 174,707 lines remain. `comp.ts`'s `file_push` unconditionally emits `"  ".repeat(fl.tab)` at the full nesting depth. `emit_match` also explicitly unpacks matched U32/F32 words into bits; a complete fix needs to distinguish formatting overhead from the nested matcher itself.

A control using the same unique spellings as immutable data with `String.eq` (`tests/compiler-string-table.bend`) emits 108,544 bytes in 0.35 seconds, peak RSS 200,732 KiB. These are one-shot compiler measurements on a shared host, with different source strategies and an unchanged compiler; they do not establish runtime throughput or an accepted compiler fix. Raw counts/timings are in `docs/bend-issues/2026-09-19-string-pattern-codegen.json`. Reproduce using `/usr/bin/time -f 'elapsed=%e peak_kib=%M' bend <fixture> -o <output.c>`; do not run multiple large compiler jobs together.

The production decoder now classifies names through an immutable table and dispatches through a native event-kind sum. Its fixture emits 25,776,794 bytes; all 1,146 boundary vectors pass before and after on one/four native threads. The original long-pattern source remains as a compiler reproducer. No compiler patch was made or installed. Candidate investigation: bound diagnostic indentation without changing emitted tokens, then separately investigate compact native literal-word comparisons while preserving ownership and fallback semantics. Any patch still needs controlled correctness/time/memory comparisons before adoption.

### BEND-001/BEND-016 follow-up: raw SSE-to-Responses integration (2026-09-19)

The installed compiler could type-check the complete new pipeline but was stopped by the sampled 40 GiB guard at 42,151,588 KiB RSS before writing C. The retained fixture is `packages/ai/test/openai-responses-pipeline.bend`; inputs and expected snapshots are runtime arguments, not generated per-case code. The established isolated memory candidate (telescope-cache clearing and per-pass forced GC, with Bun `--smol`) completed with sampled RSS at most 16,053,200 KiB during observation and emitted 66,308,279 bytes of C. ## BEND-021 — Character scalar validation differs by backend

`tests/compiler-char-scalar.bend` constructs a character from a runtime numeric argument and feeds its one-character string to the pure UTF-8 encoder.
