# Bend bug and performance investigations

This is the living investigation log for problems encountered while building pi-bend. The project is also a contribution to Bend: use idiomatic functional representations, investigate toolchain failures, and develop reusable library facilities. A workaround does not close an issue. High RSS alone does not establish a memory leak. Application inefficiency must be distinguished from a compiler or runtime defect.

Missing primitives are our implementation responsibilities, not defects awaiting an upstream fix. Track their implementation and integration with the code and [architecture plan](architecture.md#runtime-and-standard-library-implementation). Historical facility entries below retain their identifiers for existing links; their absence is not an external blocker.

Last updated: 2026-09-19. Current local compiler: Bend 2.0.7, Bun 1.4.0, with eight local patches listed in [patches/README.md](../patches/README.md). Automatic updates remain enabled; reproduce against recorded source hashes as well as version strings. No upstream issue/PR submission is recorded for these entries.

## BEND-001 — Native compilation consumes tens of GiB

[Direct layout equality](bend-issues/2026-09-21-layout-equality.json) is now installed in both compiler paths. The full Bun CPU profile attributed 6,667 of 19,329 samples (34.5%) to `JSON.stringify` directly inside `lay_eq`. That comparison now checks storage kinds, constructor arms, field offsets and nested layouts directly, without a cache. The unchanged full fixture compiles in **123.96 seconds / 7.29 GiB**, versus 190.61 seconds / 7.47 GiB, with byte-identical C: about **35% faster**. The three-pair classifier median improves from 3.71 to 3.53 seconds; ten additional tiny-fixture pairs show typed-do at 154.7→153.1 ms and AES at 302.5→296.5 ms. Generic proofs, 65,536 valid-layout differential comparisons, compiler regressions and native one/four-thread plus JavaScript literal/capture checks pass. The default build path passes concurrent callback invocation after installation. One full run per version and shared-host sampling do not establish universal performance guarantees. Bun stays the production compiler host; speed is now the priority over further RSS reductions. A separate post-install stage run emits identical C and measures 3.66 seconds loading/parsing, 12.86 seconds checking, 105.20 seconds code generation and 0.12 seconds output writing (122.84 seconds process elapsed). The installed compiler has no persistent checked-module artifacts. Caching loading/checking alone could eliminate at most roughly 13% of this fixture’s build time before cache overhead; larger incremental-build improvements require backend reuse too.

[Broader allocation-stack sampling](bend-issues/2026-09-21-host-allocation-profile.json) now covers V8 allocations outside the six previously instrumented factories, including collected temporary objects. Bun 1.4.0 rejected the inspector allocation-sampling methods, so this diagnostic runs the unchanged compiler sources under Node 24.18.0 with an explicit-GC host adapter. The reduced classifier emits byte-identical C. Estimated allocation volumes are 1.28 GB during loading, 2.20 GB during checking and 2.36 GB during compilation; these are cumulative sampled allocations, not live heap or peak RSS. Syntax conversion dominates loading; `ctr_flds` is the largest backend allocation site. Function-stack attribution does not identify object types, and V8 byte weights do not establish Bun memory costs. The full provider run with Node's default stack failed after 332.79 seconds at 3.38 GiB sampled RSS with a code-generation stack overflow. With `--stack-size=4096`, Node completed in 601.52 seconds at 4.44 GiB sampled RSS and emitted byte-identical C. Correctness checks and small compiler pairs overlapped approximately the last two minutes, so this is not a controlled speed comparison with the installed Bun result (190.61 seconds / 7.47 GiB). Node is a demonstrated alternative host for native code generation; the full CLI and other backends have not been validated under Node. Gregor prioritizes speed over further memory reductions, so Bun remains the default. A profile-driven constructor-field filtering candidate avoids copying unchanged immutable arrays, but measures 188.17 seconds / 7.56 GiB on the full fixture: no material improvement over 190.61 seconds / 7.47 GiB. Its correctness checks and byte-identical full C pass; it remains uninstalled. The installed compiler remains unchanged.

**Status:** confirmed excessive memory consumption on integration fixtures; cause under investigation. Neither an application-runtime leak nor a compiler leak has been established.

The latest [adopted probe-table fix](bend-issues/2026-09-21-scoped-probes.json) clears opened runtime variables alongside their per-definition caches, preserving the persistent erased-variable sentinel. The table previously accumulated 2,902,413 entries over twelve native passes; the candidate stayed below 10,600 at observed definition boundaries. The full output is byte-identical, sampled peak is 10.08 GiB versus 10.25 GiB, and elapsed time is 319 versus 322 seconds. This is a small improvement, installed in both default compiler locations; the first pass still approaches 10 GiB. Small benchmarks are noisy (the tiny typed-do median is about 9 ms slower), so no universal performance claim follows.

The compiler process (Bun running `bend2/main.ts`, emitting C) reached roughly 58 GB RSS during Responses integration compilation and the host began swapping. These were process observations, not instrumented exact peaks. The generated terminal fixture C was approximately 46 MB. The coding agent was not executing. The terminal tests ultimately passed all 119 scenarios on one/four threads after batching them into groups of 16. This does not establish that batching fixes the cause.

The async-driver fixture, batched into eight cases, showed the same problem. A retry with `bun --smol` completed cases 0–7 on both thread counts, but compilation of cases 8–15 subsequently reached 56,569,320 KiB RSS (53.95 GiB) after 2m54s. That process was terminated to protect the shared host. Low-memory mode is therefore insufficient. The remaining driver cases are not yet verified.

The retained integration reproducer is `build/responses-stream-driver-check-8.bend`, generated by `tests/responses_stream_driver_check.py`. This is not a reduced reproducer. At the time of profiling it depended on uncommitted driver modules; these are now retained in the repository. Use `python3 tests/responses_stream_driver_check.py --generate-only` to recreate the original eight-case batches without compiling them, then invoke the guarded profiler on batch 8. Do not run large compiler experiments concurrently.

Investigation tooling: `scripts/profile-bend.py` copies the installed compiler into an ignored build directory, records compiler/input SHA-256 hashes, instruments loading, validation, dependency discovery, each generated definition and each optimization pass, and imposes an RSS cutoff. It does not patch the installation. The cutoff is sampled every 0.5 seconds and can overshoot; it is not an OS hard memory limit. Logs include process memory, pass number, definition times, segment counts and cache sizes. Generated copies and raw profiles stay outside Git.

```sh
python3 scripts/profile-bend.py tests/static-sum-layout.bend --label static-sum-example --smol --rss-limit-gib 2
python3 scripts/profile-bend.py build/responses-stream-driver-check-8.bend --label responses-example --smol --rss-limit-gib 40
```

Use a new label for each run. The small static-sum baseline completed successfully: four code-generation passes, 41 reachable definitions, 854 compiler probes, 1,127 telescope-cache entries and about 125 MiB RSS at the last recorded pass. Its first polling sample missed the short-lived peak; subsequent tooling also records Linux child peak RSS. This is a profiler smoke check, not a performance baseline for the large program.

Source inspection of `bend2/comp.ts` identifies hypotheses to test: native emission repeats complete passes until ownership/hot/static facts stabilize; `TELES` is a strong `Map` retained across definitions and passes; global `PROBES` retains every created probe without a reset. Other temporary maps are cleared by `memo_gc()` at definition boundaries. None of this alone proves which objects account for the observed memory. Do not clear caches or compiler-variable tables indiscriminately: live terms can depend on them.

Next: use the measurements below to separate pattern-lowering allocation from cache retention, compare bounded/weak cache designs, measure scaling with pattern count/length, then test a narrowly justified patch against native one/four-thread and backend regressions. Keep idiomatic generic library interfaces intact while investigating.

### Investigation results, 2026-09-19

The instrumented large input used 1.01 GiB RSS after loading, 4.84 GiB after validation and 6.81 GiB after dependency discovery. Code generation then added approximately 2,993,963 telescope-cache entries per pass. Pass six ended at 18,536,003 entries and 37.70 GiB RSS; the 40 GiB guard stopped pass seven after 114.84 seconds. The cache stores decompositions of function types; it is a strong map, so garbage collection cannot discard its keys or values while they remain stored.

The largest individual growth was `openai-responses-terminal.mapStopReason`: 632,945 new cache entries per pass. `json-string.escapeCode` added 324,245 per pass. These are short pattern-matching functions, not giant fixture literals. This narrows the investigation to compiler expansion/memoization as well as pass lifetime; it does not establish asymptotic complexity yet.

A standalone reproducer is now retained as [tests/compiler-string-match.bend](../tests/compiler-string-match.bend): six string patterns and one print. It produces approximately 78 KiB of C. Three observed unmodified-cache runs used about 687–786 MiB peak RSS and about 2.5 seconds including the profiler's polling delay. A print-only control used about 82 MiB. Counts are more stable than allocator measurements: the string-match program created 25,177 probes and 158,244 telescope-cache entries over two code-generation passes. Exact memory/timing varies between runs; no statistical benchmark or exponential-growth claim is made.

Controlled experiments on that reduced input:

| Experiment | Live heap after collection, pass 1 / pass 2 | Telescope entries, pass 2 | Interpretation |
| --- | --- | --- | --- |
| Force GC after each pass, original cache lifetime | 196.4 / 257.7 MiB | 158,244 | Cached objects remain reachable. |
| Clear `TELES` at existing `memo_gc` boundaries and force GC after each pass | 135.0 / 140.4 MiB | 11 | Much less live retained state; further compiler allocations still exist. |

The original and experimental compiler emitted byte-identical C for the reduced input; the experimental native binary printed the expected result on one and four threads. This is narrow evidence, not full compiler-patch validation. Clearing the cache without forcing collection still reached the large input's 40 GiB guard after 110.83 seconds: strong-cache retention is not the only contributor to process RSS. The combined large-input experiment is tracked separately below. Neither experiment is applied to the installed compiler.

Experimental switches are explicit: `--clear-teles` changes cache lifetime only in the copied compiler; `--gc-passes` forces Bun collection between passes. The profiler also passes a smoke compilation and an intentional low-cutoff termination check. Peak RSS is obtained for the individual child through Linux `wait4`, avoiding inherited/cumulative child-accounting measurements. The guard still only samples, so allow substantial headroom on shared machines.

The combined large-input experiment **completed all 11 passes in 170.10 seconds, peaking at 10.67 GiB RSS**. After collection, live heap stayed around 2.6 GiB across passes; RSS stayed approximately 9.5–10.5 GiB at those boundaries. This is strong evidence that cache lifetime and delayed collection contribute materially to the original memory cliff. It does not explain all of the remaining 10.67 GiB peak or establish that forced GC is the best permanent fix. A bounded or weak cache and allocation reduction deserve comparison. Global probe accumulation remains a separate lead, not the demonstrated primary cause.

The generated large-fixture C compiled with Clang `-O1`, and all eight integration cases in this batch (cases 8–15) passed on one and four threads. These compare callback ordering, tier resolution/pricing and failures with actual upstream behavior. This validates that batch under the experimental compiler, not all 32 driver cases or the broader compiler regression suite.

Selected raw measurements, compiler/input hashes, phase boundaries and largest cache increases are retained in [the measurement record](bend-issues/2026-09-19-compiler-memory.json). Large-fixture results are exploratory and do not promote the whole async-driver suite or a compiler patch to verified status. The installed compiler remains unchanged.

The isolated BEND-001 candidate is now retained as `patches/experimental/bend-compiler-memory.patch`. All seven existing toolchain regressions, canonical library types, all 32 complete async-driver comparisons and 10 original terminal-event instances pass with it, including their native thread/backend checks. This extends the candidate's evidence; it is still not applied to the installation, is Bun-host-specific, and does not resolve the remaining compilation cost or establish general compiler correctness.

## Open runtime, compiler-limit and diagnostic investigations

**BEND-009 — Dropped channel handles do not reclaim live channel rows.** The runtime foundations currently require owner-directed disposal after aliases and observers retire; see [runtime ownership](../packages/runtime/README.md). This is a resource-lifetime gap with leak risk, distinct from BEND-001. Next investigation: a minimal allocate/drop versus allocate/dispose loop, runtime row counts and steady-state memory, followed by an explicit ownership/reclamation proposal. No automatic-reclamation fix or reduced memory measurement is recorded yet. Preserve callback reentrancy and cancellation safety when designing it.

**BEND-010 — Compiler argument-count limit under large callback captures.** Recorded in [parity history](parity.md): the loop-configuration fixture exceeded the compiler's argument-count limit and was reduced by capturing less live configuration. No compiler change was retained. Exact threshold and a standalone reproducer still need reconstruction. Investigate closure environment lowering before treating fixture reshaping as a lasting solution.

**BEND-011 — Deep generated C requires an increased Clang parser limit.** `scripts/build-pure.sh` uses `-fbracket-depth=2048` because generic record match trees exceed Clang's default 256. This is a code-generation interoperability/performance concern; the flag is a workaround. Measure depth and size versus record/variant shape and reduce a failing program. Do not flatten canonical application types merely to fit generated C.

**BEND-012 — Binding/global-name collisions during module integration.** During terminal-module integration, global helpers named `number`, `signature` and `usage` were renamed after import-context name collisions. A new combined Responses test reproduced the problem in a typed `do` binding: the constrained-sampling fixture has both a global `unchanged` helper and a local `unchanged : ... <- ...` binding. Standalone execution succeeded; importing the same file failed with `expected: def, type or law; observed: :`. Copyable `+name` bindings failed with a quantified-datatype diagnostic.

The typed-do case is now a confirmed compiler defect with reduced fixture `tests/typed-do-shadow.bend` and before/after runner `tests/typed_do_shadow.py`. Cause: `parse_term_do_stmt` parsed the left-hand name as a term before checking for `:`, allowing module namespace resolution to turn a local binding into a global reference; `+name` could fail even earlier while parsing quantified types. The local fix recognizes bare typed binding syntax first and retains the original term path for nonbindings. Effectful/pure/copied/nested bindings and initializer/tail global calls pass standalone/imported on one/four native threads and JS; qualified binding names remain rejected. The seven existing compiler regressions and canonical library types also pass. `patches/bend-typed-do-shadow.patch` is applied locally as the eighth patch. Application bindings were not renamed to hide this failure. Pattern/lambda and other previously observed shadowing cases remain open; this is not a blanket resolution of BEND-012.

### BEND-012 performance audit

The typed-do patch was installed after correctness checks but before performance measurement. That sequencing was inadequate. Future patches must be minimal and pass relevant baseline performance comparisons before installation; memory improvements must be evaluated alongside time.

An initial parsing-only comparison uses otherwise identical Bend 2.0.7 sources with this one patch reversed for the baseline. `scripts/benchmark-typed-do.ts` records two variants with alternating execution order, warmup and 30 batches of 10 parses on Bun 1.4.0. Two independent runs on the shared host produced these patched/baseline median-time ratios:

| Workload | Run 1 | Run 2 |
| --- | --- | --- |
| Base | 1.005 | 0.981 |
| Base plus standalone regression | 1.026 | 1.008 |
| 400 ordinary-action functions | 0.977 | 0.980 |
| 400 typed-binding functions | 0.996 | 0.967 |

These mixed, small timing differences do not establish zero overhead. The standalone regression is slightly slower in both runs; further isolation is needed before attributing that to the patch or calling the patch performance-neutral. Both compiler versions emitted byte-identical 92,513-byte C for `tests/typed-do-shadow.bend`, establishing unchanged generated code for that fixture only. No compiler change was installed during this audit. Other seven patches have not received a comprehensive performance audit. Raw timings, hashes, environment and scope are in [the measurement record](bend-issues/2026-09-19-typed-do-performance.json). The memory experiment remains uninstalled; its successful memory reduction is not proof of acceptable compilation speed.

**BEND-017 — Match scrutinees must follow binder order.** On the locally patched Bend 2.0.7, `def example(left: Bool, right: Bool) -> Bool` with `match right left` and rows `True{} True{}` / `_ _` fails with the diagnostic that a name is a def or consumed binder. Changing only the match order to `left right` succeeds. Inspection of `match_flatten` shows that it walks the binder list in order; reaching `right` consumes the earlier `left` as an available scrutinee. This is a current pattern-lowering restriction, not evidence of global-name shadowing. It surfaced in the UTF-8 encoder helper and was handled by aligning its parameter order with its match order, without a compiler patch or behavior change. A clearer diagnostic or support for permuted scrutinees is a possible language improvement; upstream intent has not been established. This should not be folded into BEND-012's distinct typed-binding defect.

**BEND-018 — Type-checking cliff for recursive searches with repeated byte patterns.** `tests/compiler-repeated-byte-pattern.bend` reduces a stalled line-boundary helper to a recursive list search with `case 10 <> 10 <> _`. On locally patched Bend 2.0.7/Bun 1.4.0 it fails to finish a five-second check. Changing only the second literal to 11 checks in 0.14s; replacing the recursive fallback with `None{}` checks in 0.11s. Repeated 13 and repeated 0 patterns also reach three-second limits, as does retaining the repeated-10 pattern while passing the offset unchanged. A single `13 <> 10 <> 13 <> 10 <> _` pattern checks in 0.24s. Timings are observations on a shared host, not a controlled performance benchmark.

The original combined helper was observed still consuming CPU after 86 seconds at roughly 150 MiB RSS; that process was stopped when its source was superseded. An isolated loader/checker confirms loading completes, and per-definition instrumentation places the delay in checking `findBoundary`. Diagnostic copies with limits on weak-head-normalization calls/steps and alias-cycle detection did not identify the cause within their five-second limits. Nontermination and the exact cause are not proven. Next: obtain a reliable checker profile or finer phase instrumentation, then examine repeated-literal refinement and recursive-call checking. No patch was installed. The production boundary finder now uses a small prefix automaton, verified against the SDK; this is a suitable linear scanner but does not resolve the compiler finding. Reproduce with `timeout 5 bend tests/compiler-repeated-byte-pattern.bend`; this intentionally time-limited investigation is not part of the passing application suite.

**BEND-019 — JS backend stack overflow in large `List.append`.** `tests/compiler-js-list-append.bend` repeatedly doubles a 256-element list and checks that the result is nonempty. With locally patched Bend 2.0.7 and Bun 1.4.0, the native build prints `constructed`; the JS build exits 1 with `bend: memory fault (machine stack overflow?)`. **BEND-013 — Numeric and wire-format foundations.** Pure Bend modules currently supply two-limb U64/U128 arithmetic, binary64 arithmetic/decimal conversion, JSON parsing/encoding and partial streaming JSON. ## BEND-013 progress — Montgomery modular exponentiation (2026-09-22)

`BigNat.powerMod` reduced every square and multiply with the bit-serial long division behind `reduce`: one compare-and-subtract of the whole modulus per dividend bit, so a 2048-bit modulus cost about 4,096 × 128 limb operations per reduction, some 2,000 times per exponentiation. For an odd modulus (every RSA modulus and prime field) `powerMod` now keeps values in Montgomery form with R = 2^(16k) over the module's 16-bit limbs: the inverse of the low limb comes from four Newton steps, a product is reduced word by word (add the multiple of the modulus that clears the low limb, drop it, k times) and corrected by one conditional subtraction, and the ladder squares and multiplies in that form, entering and leaving it through one general reduction each. Even moduli keep the bit-serial path. `tests/big_nat_vectors.py` gains twelve `powerMod` cases against Python's `pow` (exponents 0 and 1, modulus 1, a base above the modulus, an even modulus, the P-256 prime, 1024- and 2048-bit odd moduli); all pass. On an RSA-2048 modulus (`build/powmod-bench.bend`, one native thread) the public exponent 65537 takes 0.05 s instead of 0.33 s and a full 2048-bit private exponent 3.61 s; the schoolbook 16-bit-limb list multiplication is now the cost, which 32-bit limbs with a widening multiply primitive would quarter.

## BEND-013 progress — native binary64 (2026-09-22)

Bend had a native `F32` (a 32-bit word with C/JS templates) and no `F64`; the port computed binary64 in software over U32 words (`packages/runtime/src/f64.bend`, 674 lines, with arbitrary-precision decimal conversion). `patches/bend-native-f64.patch` adds `type F64 is Data: F64{high: U32, low: U32}` to Base, the IEEE 754 bits high word first, with laws for conversion (`U32.to_f64`, `F64.to_u32`), arithmetic (`add sub mul div mod pow neg abs sqrt floor ceil trunc`), comparison (`is_eq … is_ge`; NaN is unequal to itself) and text (`show`: the fewest digits that read back exactly, laid out as ECMAScript's `Number.prototype.toString`; `read`: `strtod` without hexadecimal or parenthesised forms). Runtime terms carry 48-bit immediates, so a double is not a word: the record's two-word inline layout is the representation, and the intrinsic emitter now passes every word of every argument and lets a template array compute the result once into a scratch word (a template starting with `!`) before splitting it. The JS lane packs through a `DataView`. Metal has no `double`: there `f64_of` posts "a function the device does not hold", as `F32.show` already does on any device; CUDA computes natively. `F64` joins the runtime datatypes so `read` can build its constructor.

The runtime module keeps its API (`fromBits`, `toBits`, `decode`, `compare`, `add` …, `toDecimal`, `toJsonNumber`, `convert`, `fromRatio`, `remainder`, `truncate`, `ceil`) as a facade: arithmetic, comparison and spelling are primitives; decoding, integrality, natural-number conversion and exact ratio rounding remain pure word operations. Callers name Base's `F64` instead of `F.F64` (94 files). The pure implementation is retained as `packages/runtime/test/f64-software.bend`, the reference the primitives are checked against. A 17-case probe prints identical results on the C and JS backends (1/3, 0.1+0.2, 1e21, 1e-7, -0, nan, inf, 2^53, floor, fmod, comparisons, reads).

Spelling needed one refinement the vector harness caught: at a power of two the set of decimals that read back as the value is lopsided (the lower neighbour is half as far), so the nearest p-digit decimal can miss while the next one up lands (`2^-652`: `5.351097043477546e-197` reads back as the neighbour below, `…547` as the value; Python's `repr` agrees with the latter). The C spelling therefore also tries the mantissa one unit up or down in its last digit before moving to more digits; the JS lane uses the engine's own shortest spelling.

Measured in `build/f64-bench.bend` (native, one thread, same seed, identical outputs): one million multiply-adds take 3.81 s in software and under 10 ms natively; twenty thousand decimal spellings take 12.16 s in software and 0.14 s natively. With the F64 toolchain the proof gate passes on the migrated laws, the five binary64 harnesses pass (arithmetic vectors, decimal, ratio, remainder, natural conversion on native one/four threads and Bun), and every file importing the module type-checks except two fixtures with unrelated pre-existing standalone limits. The full harness run on the migrated tree is recorded with the installation.

## BEND-001 resolution — worklist emission (2026-09-22)

The emitter is the ownership/heat analysis: it emitted every reachable definition, callees first, and repeated the whole pass whenever the fact sets (`own`, `hot`, `stat`) grew, keeping the pass that changed nothing. On the native agent that was 12 passes of about 6 s over 4,658 definitions, because a fact discovered at a call site reaches its callee only in the next pass and a call chain is many links long. Alternating the emission order did not help (12 passes either way).

`patches/bend-worklist-emission.patch` makes the fact sets remember which unit read each fact (a unit is a definition together with the spins of calls to it), and a fact that grows dirties exactly its readers. Every unit is emitted once; then only dirty units are emitted again, their old segments, spins and lend contributions dropped first, until no unit is dirty: every retained output was produced under the final facts, the same invariant the last kept pass had. Lends are rebuilt from the retained outputs before their closure each round; `own`, `hot` and `stat` only grow, as before. Rounds on the native agent: 4,658, 3,735, 307, 58, 39, 23, 6, 6, 6, 5, 6 units; emission 85 s → 43 s at 3.7 GiB (checker 5 s, rounds 29 s, assembly 0.6 s), C 25.4 MB. The fixed point reached is a different post-fixed point (one fewer heated type, five more static constructors), which is expected of an order-dependent monotone analysis. Two emission defects surfaced: the spin counter lived in the file state that a nested spin emission restores, so names repeated; and a spin emitted again lands after its callers, so all spins are now declared before their bodies.

Clang on the resulting 25.4 MB takes 157 s at `-O1` and 19 s at `-O0` (`PI_BEND_OPT=-O0` in `scripts/build-pure.sh`), which is the setting to use for development iterations. Validation: proof gate; 44 of the table-heavy 45-harness subset (the review report fails on every compiler); `tests/native-agent.bend` builds in 299 s including Clang and passes its loopback HTTPS tool-loop check on one and four threads. With the installed compiler all 246 runnable merge harnesses pass (231 in the parallel run; 13 that ran while the tree was briefly modified, one whose binary was being rebuilt concurrently and one DNS port collision passed on serial rerun; the remaining 7 entries need candidate/baseline arguments on every compiler).

## BEND-016 resolution — word-literal match arms (2026-09-22)

Cause, confirmed by reading `match_flatten`: a literal pattern `case 42:` or a string character is parsed as `U32{WCon{b0, .. WNil{}}}`, and the row flattener specialised that column one constructor at a time, so every character became 32 nested `Mat`s on bits, and each bit's default re-flattened all remaining rows. The default rows (including the wildcard arm) were therefore copied once per bit per literal, which is the quadratic growth behind BEND-016, BEND-022, BEND-023 and BEND-025; the C backend then unpacked the word into 32 bit tests per character.

Fix (`patches/bend-word-literal-arms.patch`, installed in `build/bend-native-toolchain`): when a column's constructor patterns are all complete `U32` literals, `match_flatten` emits one `Mat` arm per distinct literal, carrying the word in a new optional field `w`; the default is flattened once per literal. `Mat.w` is propagated by the term traversals, shown and compared; the checker checks a literal arm's body at `P(literal)` and the rest over the whole `U32` type (a literal chain therefore needs a default arm, as before); `term_wnf` compares a constant scrutinee against the literal and treats a non-constant word as stuck; the C backend emits `word == literal` comparisons and passes the word to the default, and the JS backend emits `=== literal`. `def_raise` counts no field for a literal arm and constant folding of literal matches follows the same comparison. The arity diagnostic now names the offending segments.

Evidence (same host, shared with other builds, one run each unless stated): `tests/compiler-long-string-patterns.bend` emits 751,681 bytes in 0.40 s (peak 120 MiB) versus 10,669,154 bytes in 5.32 s (550 MiB), and both binaries classify all sixteen names, three near misses and the empty string identically. `packages/agent/test/agent.bend` emits 2,772,107 bytes in 4.14 s (595 MiB) versus 176,735,131 bytes in 25.43 s (3.2 GiB); Clang `-O1` takes 40.1 s versus 294.4 s; the resulting program passes its 20 cases on one and four threads. The proof gate (502 laws) passes under the patched compiler. Of the 253 merge harnesses, 245 pass under both compilers (DNS harnesses run serially) with total wall time 16,924 s versus 13,580 s, none fails only under the patched compiler, and the remaining entries are invocation-only failures (they need candidate/baseline arguments) on both. `tests/openai-responses.bend` still fails with `an arity over 255` under both compilers (BEND-010; the provider harness keeps using the layout-cap copy for C).

Not changed: string patterns still nest one `SCon` test per character, and rows with wildcard tails are still duplicated per literal at each position; `F32` literal patterns keep the bit path; `Nat` literals keep their `Succ` chains and tables.

## BEND-031 — Multi-scrutinee matches must follow parameter order (2026-09-22)

`tests/compiler-match-parameter-order.bend` matches `match first second` where `first` is the def's last parameter and `second` an earlier one. Bend 2.0.7 with the installed patches rejects it before code generation with `a match on a parameter or field (this name is a def or a consumed binder: give the value its own def)`; writing `match second first` with the columns swapped type-checks and runs. The message names the wrong cause: neither name is a def or consumed. Inspection of `match_flatten` in `bend2/bend.ts` shows the flattener consuming the def's parameter list left to right and reaching a `Var` scrutinee with no parameters left, which it reports as the def/consumed-binder case. Status: confirmed restriction (or a flattener bug; the intended rule is undocumented). Workaround used throughout the print-CLI port: declare scrutinized parameters last, in scrutinee order. Regression: `bun build/bend-native-toolchain/bend2/main.ts tests/compiler-match-parameter-order.bend` (fails today; passes after swapping the scrutinees).

## BEND-032 — Pattern binders resolve to same-module defs once the module is imported (2026-09-22)

`tests/compiler-def-named-binder-lib.bend` defines `def text(value)` and matches `case Wrapped{text}: text`. Checked alone the module passes (`All terms check`); `tests/compiler-def-named-binder.bend`, which merely imports it, fails with `expected: a pattern (a binder or a constructor); observed: compiler-def-named-binder-lib.text`. Under an import the module's defs are namespaced and the pattern binder is resolved as a reference to the def instead of a fresh name. This is BEND-012's name-resolution family, now observable for lowercase defs: a def named like a common field (`text`, `read`, `list`, `entries`, `request`) silently changes meaning of every pattern that binds that name in the same file. Status: confirmed defect, standalone checks do not catch it. Workaround: never bind a pattern variable with the name of a def in the same module. Regression: `bun build/bend-native-toolchain/bend2/main.ts tests/compiler-def-named-binder.bend`.

### Language restrictions met while porting the print CLI (2026-09-22)

Not defects, recorded because they shape the code: definitions cannot refer forward, so mutual recursion is impossible and loops that would call a later helper carry their decision as data (`Step`/`Scan` records, fuel-counted `parseLoop`); a template function passed to `Callback.create` must not mark parameters affine-copyable (`+x`), the copy happens in a wrapper; tuple types are `Type`, so a `Maybe` of two strings needs a `Data` record; `match` cannot scrutinize a computed expression (a helper def takes the value as a parameter); and a bare `+x = ...` binding cannot be matched afterwards.

### Language restrictions met while porting session persistence (2026-09-22)

Also not defects: a template (`~f`) parameter must be a definition or a lambda — a record of functions passed as a template is a compile-time constant, but its fields cannot be projected into template positions ("a defined name" is expected of `fs.show`, and matching the record is refused as an "undestructed scrutinee"), so the session codec takes its six encoder/decoder functions as separate template parameters; `where` is a keyword, so it cannot name a binder; a `+`-marked pattern binder whose name equals a definition in the same module parses as an affine type marker (`+started` → "expected a quantified datatype after +"), which is BEND-032 in another guise; a `match` cannot follow a bind inside a `do` block ("a match heads a def body, not a term"), so every decision after an effect is a helper definition; and Bend's termination check reads the arguments left to right, so an accumulator must follow the shrinking list (`scanBytes(bytes, state)`, not `scanBytes(state, bytes)`). A lambda binder may not share a name with a definition in its module either (`state => …` next to `def state`), a callback body's environment parameter cannot be marked copyable (copy inside a wrapper def), a `+x : T <- …` bind in a `do` block is allowed but a `+x = …` line after a bind is not, and an `IO` loop that continues while a runtime condition holds needs a shrinking argument for the termination check (`drainQueued(fuel, agent)`).

### BEND-019 resolved in the JS emitter: explicit continuation stack (2026-09-22)

Cause: the JS backend trampolines tail calls (`run_jump`/`run_loop`) but a self-call that is not in tail position — a constructor field (`h <> f(t)`), an arithmetic operand (`nat_chk(f(t) + 1n)`), a string concatenation (`h + (sep + f(t))`) or an argument of another call (`String.split`'s `fin(h, f(t), …)`) — was emitted as a nested JavaScript call, and JavaScriptCore's stack, which Bun cannot enlarge, overflowed near 65,000 frames while the native backend was fine. Base rewrites were ruled out earlier because a proof unfolds `List.length` definitionally.

Fix (`patches/bend-js-explicit-stack.patch`, installed in the CLI worktree toolchain): `js_stackify` post-processes each def's emitted lines. When an arm contains a non-tail self-call, the def becomes `$outer: while (true) { … }` with a heap array `$stack`: the first self-call of an arm pushes the rest of that arm as a closure over that iteration's constants (parameters are rebound as `const` per iteration) and continues with the callee's arguments; tail self-calls continue; other returns set `$result` and break; afterwards the frames are applied innermost first through `run_loop`. Closures inside arms and a second self-call in the same arm keep ordinary recursion, which is what tree-shaped recursion needs anyway. The C backend does not go through this pass.

Evidence: `tests/js_explicit_stack.py` — `tests/compiler-js-list-append.bend` (doubling to 65,536 elements) prints `constructed` on Bun in 0.03 s and the native build agrees; `tests/compiler-js-list-length.bend` (`List.length` over 200,000 elements, `String.split` over 50,000 separators, `String.join` over 20,000 parts) prints `200000 50001 40001` on Bun in 0.13 s. The JS build of the coding-agent CLI has 821 rewritten defs, is 3% larger (10.62 → 10.96 MB) and starts in the same 0.15 s (`--help`, three runs each); the config-value, system-prompt and auth-storage harness Bun lanes and a live JSON-mode prompt through the JS CLI pass unchanged. Status: resolved for self-recursion; mutual recursion is impossible in Bend (no forward references), so no case is left open on the JS lane besides deep closure-internal recursion.
