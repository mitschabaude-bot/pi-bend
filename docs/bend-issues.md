# Bend issues and standard-library opportunities

This is the living investigation log for problems encountered while building pi-bend. The project is also a contribution to Bend: use idiomatic functional representations, investigate toolchain failures, and develop reusable library facilities. A workaround does not close an issue. High RSS alone does not establish a memory leak. Application inefficiency must be distinguished from a compiler or runtime defect.

Last updated: 2026-09-19. Current local compiler: Bend 2.0.7, Bun 1.4.0, with eight local patches listed in [patches/README.md](../patches/README.md). Automatic updates remain enabled; reproduce against recorded source hashes as well as version strings. No upstream issue/PR submission is recorded for these entries.

## BEND-001 — Native compilation consumes tens of GiB

**Status:** confirmed excessive memory consumption on integration fixtures; cause under investigation. Neither an application-runtime leak nor a compiler leak has been established.

The compiler process (Bun running `bend2/main.ts`, emitting C) reached roughly 58 GB RSS during Responses integration compilation and the host began swapping. These were process observations, not instrumented exact peaks. The generated terminal fixture C was approximately 46 MB. The coding agent was not executing. The terminal tests ultimately passed all 119 scenarios on one/four threads after batching them into groups of 16. This does not establish that batching fixes the cause.

The async-driver fixture, batched into eight cases, showed the same problem. A retry with `bun --smol` completed cases 0–7 on both thread counts, but compilation of cases 8–15 subsequently reached 56,569,320 KiB RSS (53.95 GiB) after 2m54s. That process was terminated to protect the shared host. Low-memory mode is therefore insufficient. The remaining driver cases are not yet verified.

The retained integration reproducer is `build/responses-stream-driver-check-8.bend`, generated by `tests/responses_stream_driver_check.py`. This is not a reduced reproducer. At the time of profiling it depended on uncommitted driver modules; these are now retained in the repository. Use `python3 tests/responses_stream_driver_check.py --generate-only` to recreate the original eight-case batches without compiling them, then invoke the guarded profiler on batch 8. Do not run large compiler experiments concurrently.

Investigation tooling: `scripts/profile-bend.py` copies the installed compiler into an ignored build directory, records compiler/input SHA-256 hashes, instruments loading, validation, dependency discovery, each generated definition and each optimization pass, and imposes an RSS cutoff. It does not patch the installation. The cutoff is sampled every 0.5 seconds and can overshoot; it is not an OS hard memory limit. Logs include process memory, pass number, definition times, segment counts and cache sizes. Generated copies and raw profiles stay outside Git.

```sh
python3 scripts/profile-bend.py tests/static-sum-layout.bend --label static-sum-example --smol --rss-limit-gib 2
python3 scripts/profile-bend.py build/responses-stream-driver-check-8.bend --label responses-example --smol --rss-limit-gib 40
```

Use a new label for each run. The small static-sum baseline completed successfully: four code-generation passes, 41 reachable definitions, 854 compiler probes, 1,127 telescope-cache entries and about 125 MiB RSS at the last recorded pass. Its first polling sample missed the short-lived peak; subsequent tooling also records Linux child peak RSS. This is a profiler smoke check, not a performance baseline for the large program.

Source inspection of `bend2/comp.ts` identifies hypotheses to test: native emission repeats complete passes until ownership/hot/static facts stabilize; `TELES` is a strong `Map` retained across definitions and passes; global `PROBES` retains every created probe without a reset. Other temporary maps are cleared by `memo_gc()` at definition boundaries. None of this alone proves which objects account for the observed memory. Do not clear caches or compiler-variable tables indiscriminately: live terms can depend on them.

Next: use the measurements below to separate pattern-lowering allocation from cache retention, compare bounded/weak cache designs, measure scaling with pattern count/length, then test a narrowly justified patch against native one/four-thread and backend regressions. Keep idiomatic generic library interfaces intact while investigating.

### Investigation results, 2026-09-19

The instrumented large input used 1.01 GiB RSS after loading, 4.84 GiB after validation and 6.81 GiB after dependency discovery. Code generation then added approximately 2,993,963 telescope-cache entries per pass. Pass six ended at 18,536,003 entries and 37.70 GiB RSS; the 40 GiB guard stopped pass seven after 114.84 seconds. The cache stores decompositions of function types; it is a strong map, so garbage collection cannot discard its keys or values while they remain stored.

The largest individual growth was `openai-responses-terminal.mapStopReason`: 632,945 new cache entries per pass. `json-string.escapeCode` added 324,245 per pass. These are short pattern-matching functions, not giant fixture literals. This narrows the investigation to compiler expansion/memoization as well as pass lifetime; it does not establish asymptotic complexity yet.

A standalone reproducer is now retained as [tests/compiler-string-match.bend](../tests/compiler-string-match.bend): six string patterns and one print. It produces approximately 78 KiB of C. Three observed unmodified-cache runs used about 687–786 MiB peak RSS and about 2.5 seconds including the profiler's polling delay. A print-only control used about 82 MiB. Counts are more stable than allocator measurements: the string-match program created 25,177 probes and 158,244 telescope-cache entries over two code-generation passes. Exact memory/timing varies between runs; no statistical benchmark or exponential-growth claim is made.

Controlled experiments on that reduced input:

| Experiment | Live heap after collection, pass 1 / pass 2 | Telescope entries, pass 2 | Interpretation |
| --- | --- | --- | --- |
| Force GC after each pass, original cache lifetime | 196.4 / 257.7 MiB | 158,244 | Cached objects remain reachable. |
| Clear `TELES` at existing `memo_gc` boundaries and force GC after each pass | 135.0 / 140.4 MiB | 11 | Much less live retained state; further compiler allocations still exist. |

The original and experimental compiler emitted byte-identical C for the reduced input; the experimental native binary printed the expected result on one and four threads. This is narrow evidence, not full compiler-patch validation. Clearing the cache without forcing collection still reached the large input's 40 GiB guard after 110.83 seconds: strong-cache retention is not the only contributor to process RSS. The combined large-input experiment is tracked separately below. Neither experiment is applied to the installed compiler.

Experimental switches are explicit: `--clear-teles` changes cache lifetime only in the copied compiler; `--gc-passes` forces Bun collection between passes. The profiler also passes a smoke compilation and an intentional low-cutoff termination check. Peak RSS is obtained for the individual child through Linux `wait4`, avoiding inherited/cumulative child-accounting measurements. The guard still only samples, so allow substantial headroom on shared machines.

The combined large-input experiment **completed all 11 passes in 170.10 seconds, peaking at 10.67 GiB RSS**. After collection, live heap stayed around 2.6 GiB across passes; RSS stayed approximately 9.5–10.5 GiB at those boundaries. This is strong evidence that cache lifetime and delayed collection contribute materially to the original memory cliff. It does not explain all of the remaining 10.67 GiB peak or establish that forced GC is the best permanent fix. A bounded or weak cache and allocation reduction deserve comparison. Global probe accumulation remains a separate lead, not the demonstrated primary cause.

The generated large-fixture C compiled with Clang `-O1`, and all eight integration cases in this batch (cases 8–15) passed on one and four threads. These compare callback ordering, tier resolution/pricing and failures with actual upstream behavior. This validates that batch under the experimental compiler, not all 32 driver cases or the broader compiler regression suite.

Selected raw measurements, compiler/input hashes, phase boundaries and largest cache increases are retained in [the measurement record](bend-issues/2026-09-19-compiler-memory.json). Large-fixture results are exploratory and do not promote the whole async-driver suite or a compiler patch to verified status. The installed compiler remains unchanged.

The isolated BEND-001 candidate is now retained as `patches/experimental/bend-compiler-memory.patch`. All seven existing toolchain regressions, canonical library types, all 32 complete async-driver comparisons and 10 original terminal-event instances pass with it, including their native thread/backend checks. This extends the candidate's evidence; it is still not applied to the installation, is Bun-host-specific, and does not resolve the remaining compilation cost or establish general compiler correctness.

## Open runtime, compiler-limit and diagnostic investigations

**BEND-009 — Dropped channel handles do not reclaim live channel rows.** The runtime foundations currently require owner-directed disposal after aliases and observers retire; see [runtime ownership](../packages/runtime/README.md). This is a resource-lifetime gap with leak risk, distinct from BEND-001. Next investigation: a minimal allocate/drop versus allocate/dispose loop, runtime row counts and steady-state memory, followed by an explicit ownership/reclamation proposal. No automatic-reclamation fix or reduced memory measurement is recorded yet. Preserve callback reentrancy and cancellation safety when designing it.

**BEND-010 — Compiler argument-count limit under large callback captures.** Recorded in [parity history](parity.md): the loop-configuration fixture exceeded the compiler's argument-count limit and was reduced by capturing less live configuration. No compiler change was retained. Exact threshold and a standalone reproducer still need reconstruction. Investigate closure environment lowering before treating fixture reshaping as a lasting solution.

**BEND-011 — Deep generated C requires an increased Clang parser limit.** `scripts/build-pure.sh` uses `-fbracket-depth=2048` because generic record match trees exceed Clang's default 256. This is a code-generation interoperability/performance concern; the flag is a workaround. Measure depth and size versus record/variant shape and reduce a failing program. Do not flatten canonical application types merely to fit generated C.

**BEND-012 — Binding/global-name collisions during module integration.** During terminal-module integration, global helpers named `number`, `signature` and `usage` were renamed after import-context name collisions. A new combined Responses test reproduced the problem in a typed `do` binding: the constrained-sampling fixture has both a global `unchanged` helper and a local `unchanged : ... <- ...` binding. Standalone execution succeeded; importing the same file failed with `expected: def, type or law; observed: :`. Copyable `+name` bindings failed with a quantified-datatype diagnostic.
+
+The typed-do case is now a confirmed compiler defect with reduced fixture `tests/typed-do-shadow.bend` and before/after runner `tests/typed_do_shadow.py`. Cause: `parse_term_do_stmt` parsed the left-hand name as a term before checking for `:`, allowing module namespace resolution to turn a local binding into a global reference; `+name` could fail even earlier while parsing quantified types. The local fix recognizes bare typed binding syntax first and retains the original term path for nonbindings. Effectful/pure/copied/nested bindings and initializer/tail global calls pass standalone/imported on one/four native threads and JS; qualified binding names remain rejected. The seven existing compiler regressions and canonical library types also pass. `patches/bend-typed-do-shadow.patch` is applied locally as the eighth patch. Application bindings were not renamed to hide this failure. Pattern/lambda and other previously observed shadowing cases remain open; this is not a blanket resolution of BEND-012.

## Standard-library development opportunities

**BEND-013 — Numeric and wire-format foundations.** Pure Bend modules currently supply two-limb U64/U128 arithmetic, binary64 arithmetic/decimal conversion, JSON parsing/encoding and partial streaming JSON. These are reusable library candidates, not reasons to introduce JavaScript value semantics. Evaluate which belong in Base versus separate packages; retain independent arithmetic and codec conformance tests. Lack of native binary64 operations may also be a performance issue, but no comparative benchmark is recorded here yet.

**BEND-014 — Async library ownership and callback ergonomics.** `Callback`, `Deferred`, cancellation, persistent FIFO and event streams are implemented as typed Bend modules. Affine closures and explicit resource ownership shape their APIs; those language features are not defects merely because TypeScript differs. Investigate reusable standard interfaces, safe disposal, reentrancy and observer cancellation; avoid synchronized cells for ordinary data and do not add unrestricted mutation to imitate JS.

**BEND-015 — HTTP/TLS and remaining system facilities.** Native networking and the provider transport remain unfinished. The bootstrap's libcurl adapter is not the accepted final dependency. Before designing each facility, inspect Bend's current primitives and document the exact missing operation, minimal OS boundary, reusable pure-Bend layer and tests. This entry records project needs, not a verified claim that every such facility is absent from the current release.
