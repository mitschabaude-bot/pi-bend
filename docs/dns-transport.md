# Resolver transport work

The system configuration loader now prepares the native UDP/TCP resolver, including timeout budgets, retry counts, transport selection, request options and persistent rotation. Explicit TCP APIs remain available. This is not complete system hostname resolution: hosts-file integration, address-family orchestration and remaining related option semantics, reload integration and adoption of the isolated runtime/compiler candidates remain unfinished. The sections below record the implementation milestones; their earlier pending-work notes describe their state at that milestone.

## Scheduling boundary

The pinned [glibc 2.39 transport implementation](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/res_send.c) distinguishes the transports. `__res_context_send` makes one server pass for TCP; the `attempts` count drives UDP rounds. TCP permits one reconnect for a reset during length-prefix reading. The parsed retransmission interval is used by the UDP path. Its timeout depends on server index and server count, with a minimum of one second. These details belong to the datagram scheduler, not a new outer retry loop around the TCP resolver.

Our explicit total deadline remains a caller limit spanning TCP candidates, aliases, server failover and the permitted reset recovery. Keeping that deadline also avoids inheriting the reference TCP path's blocking-wait behavior. Parsed timeout/attempt values remain in the retained configuration for the UDP implementation.

## Original UDP implementation boundary

The original Bend UDP effects use string payloads and IPv4 socket addresses, without a receive truncation indicator. The isolated UDP candidate now supplies binary payloads, IPv4 and IPv6 endpoints, and explicit detection of truncated datagrams. Complete correctness, resource and relevant performance checks before adoption. Keep DNS parsing, query matching, retry decisions, EDNS policy and search behavior in pure Bend.

The datagram API must preserve datagram boundaries and zero-length packets, distinguish an empty packet from EOF, expose the peer endpoint, reject invalid lengths/bytes, and close or cancel pending operations without leaked resources. Validate it against loopback sockets with binary/non-UTF-8 payloads, oversized packets, both address families and cancellation races. Integrate a pure scheduling state machine with generic laws before wiring the UDP driver into transport selection and TCP fallback.

## UDP cancellation finding and implementation

The existing TCP socket-interrupt owner must not wrap pending UDP receives. A reduced Linux probe shows that shutdown on an unconnected UDP socket returns ENOTCONN; a connected socket accepts shutdown, but both then report readiness while nonblocking receive returns EAGAIN. The resulting receive callback parks again. All six Bend probes (IPv4/IPv6 on native one/four threads and Bun) remained pending for the bounded observation interval. [Evidence](runtime-validation/2026-09-20-udp-interrupt-investigation.json) records the OS and Bend observations. This is an unsupported composition, not evidence that the TCP interrupt contract is broken.

Implement operation-level cancellation in the isolated UDP candidate. Use the existing cancellable timer model: an affine operation owner, independently copyable cancellation capability, explicit completion/cancelled states, and queue removal on cancellation. A pending read must return socket ownership and a distinct cancellation outcome without manufacturing an empty datagram or shutting down the socket. Join the operation before retiring its owner. Stale cancellation capabilities must not affect a reused operation slot. Completion already committed by the IO loop must beat later cancellation. Keep all new state and cancellation work in the new effects so existing IO paths remain unchanged.

Validate cancellation before wait, while parked, after completion, repeated/competing cancellation, owner reuse, packet arrival races, and descriptor/activation cleanup. Only then wire abort/deadline scopes to the datagram driver. This is implementation work in this project; it is not a request for an external primitive to be supplied.

Both operation primitives are implemented in the isolated candidate as `UDPRead.new/wait/cancel/release` and `UDPWrite.new/wait/cancel/release`. Read packet-arrival races, cancellation/completion, stale capabilities and socket reuse are validated. Send parking, retry and cancellation use explicit test-only EAGAIN injection; real OS send-buffer saturation is not claimed. Native teardown audits check operation rows, timers, channels, parked waits and sockets in fd range 0–4095. Pure Bend `abortable-datagram.recv/send` wrappers register removable abort observations and join their watchers before returning. Existing generic abort-outcome laws cover final precedence for both result types. These milestones are detailed in the parity records. Broader concurrent resource stress and performance evaluation still precede adoption; the UDP driver and scheduling state machine remain to be implemented.

## Implemented retry sequence core

`dns-udp-schedule` now supplies a generic immutable cursor over repeated passes through one selected server order. It retains the order across rounds, preserves duplicate entries, emits one entry per step and exhausts without an attempt when the count or server list is empty. Its generic laws specify the entire remaining sequence. The driver must supply entries carrying original configuration indices before rotation: the pinned reference computes each server's timeout from that original index, not its position in the rotated visit order. Timeout construction, policy validation, transport transitions and actual UDP exchanges remain to be wired to this cursor. The pure scheduling work can proceed against the isolated runtime candidate without adopting its effects into the installed compiler.

## Implemented timeout calculation

`dns-udp-timeout` represents original positions as `First`, `SecondOfTwo`, `SecondOfThree` and `ThirdOfThree`. The supported domain comes from [glibc 2.39's three-server limit](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/bits/types/res_state.h). Within the [parsed timeout range 0–30](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/resolv.h), it implements the [datagram budget formula](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/res_send.c): the first server uses the base seconds, later original indices scale by their power of two and divide by server count, and every result has a one-second minimum. The largest supported result is 40 seconds. Direct inputs above 30 return a typed error; the existing option parser retains its documented cap.

The duration type represents strictly positive whole seconds. Generic laws cover positivity, preservation/flooring and equal budgets for both positions in a two-server setup. Compiled reference-formula checks cover every parsed base timeout and valid original position. Position assignment to configured entries, configuration acceptance for excess server entries, conversion into attempt deadline scopes and actual exchanges remain integration work. The timeout module does not decide those policies implicitly.

## Prepared server entries

`dns-udp-plan.prepare` now attaches position metadata before rotation and calculates each entry's duration. Its successful result is a complete list of `Attempt{server, position, duration}` values suitable for `dns-server-source`/`dns-server-rotation` and `dns-udp-schedule`; duplicate server payloads remain separate positioned entries. The UDP preparation boundary returns typed errors for zero or more than three entries, preserving strict rejection instead of silent truncation. This boundary is not yet used by the system loader or live resolver, so existing configuration acceptance remains unchanged. The loader still retains all source settings/diagnostics for final policy integration. Invalid layout errors precede timeout validation; no partial plan is exposed.

The remaining driver work must consume these prepared entries, create nested attempt deadlines under the caller's total deadline, encode/send queries, validate incoming peers and replies, choose retry/stop/TCP fallback, and retire each attempt before continuing. The composition fixture checks ordering and budgets without performing network exchanges.

## Attempt deadline scopes

`dns-udp-attempt-scope.create` now borrows the existing total-deadline signal and creates a child scope from a prepared duration. The checked conversion accepts the supported 1–40 seconds and rejects manually constructed larger durations before creating a timer. A generic law establishes rejection for any excess natural value. The child scope preserves its parent's reason: the adapter distinguishes local attempt expiry from parent abort, including the total deadline expiring and supplied/default caller aborts.

`close` must run after all operations borrowing the child signal settle. It delegates cancellation and joins to the existing deadline owner and returns the classified settled reason. Repeated attempts reuse the same total-deadline signal; they do not reset the caller's clock. Loopback exchange code must still own its socket, send and receive under this child signal, and finish cleanup before creating the next attempt. This adapter is validated against the isolated timer candidate and is not yet a complete UDP driver.

## Single UDP query exchange

`datagram-peer` now owns a dedicated socket associated with the numeric DNS peer. Association is needed before inspecting local metadata: a wildcard bind address alone does not identify the route chosen for a destination. The new isolated `UDP.connect_peer` effect only performs this OS operation; route ownership and DNS behavior stay in Bend.

`dns-udp-query.exchangeRequest` validates/encodes the immutable query (including optional EDNS), checks retained abort, opens the peer, sends and receives under the caller's borrowed attempt signal, and closes the socket before returning. It uses the existing strict datagram transaction matcher with actual local/remote endpoints, ID, opcode and question. Malformed/unrelated packets do not reset the deadline; matching TC replies return a truncation result for later TCP fallback. DNS wire messages above the 65,535-byte receive capacity are ignored without trusting a partial header. Successful RCODE replies stay responses for higher-level policy. The read loop uses the existing explicit termination annotation for repeated awaited IO; liveness and teardown are exercised by integration tests rather than claimed as pure theorems.

Loopback tests compose this exchange with the prepared attempt-scope lifecycle. The server driver below adds repeated transport attempts; response-code/EDNS fallback policy, TCP fallback and adoption into the system resolver remain unfinished. The TCP resolver remains the live configured resolver.

## Ordered UDP server driver

`dns-udp-servers.exchangeRequest` consumes the complete prepared/rotated entries and retry count, borrows one total-deadline signal, and reuses the immutable request through ordered rounds. Each attempt owns a child deadline and a dedicated peer socket. The query closes the socket and joins operation observers before the driver closes the child scope; only then can the next attempt begin. Local timeout, datagram socket failure and numeric peer-association failure permit failover. Invalid destination ports, oversized budgets, encoding errors, other setup failures and inherited aborts stop with typed errors. An error report retains the selected endpoint, primary failure and cleanup-time deadline reason. Exhaustion retains only the last report, without accumulating a history proportional to retries.

A reply returns its selected endpoint, including for truncation, so the next transport-policy layer can target that same server for TCP fallback. A completed reply remains successful if closing its scope observes a later expiry. This is still a transport-failure driver: RCODE/EDNS policy and TCP fallback remain above it and are not yet implemented here. The configured live resolver still uses TCP.

The driver recurses structurally over a natural-number budget equal to rounds times server count. A new generic `initial_count` law proves that this budget equals the complete initial cursor sequence length; the existing `next_sequence` law specifies each emitted entry and remaining sequence. An internal `InvalidCursor` result exposes an inconsistent budget instead of silently truncating the schedule. These are pure sequence/count proofs, not proofs of IO cleanup or clock behavior. Integration tests exercise the effectful composition and teardown against the isolated runtime candidate.

## UDP response disposition

`dns-udp-policy` now classifies a transaction-matched header into acceptance, same-server TCP fallback, or retry with a typed rejection reason. It follows the pinned [glibc 2.39 single-query decision order](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/res_send.c): SERVFAIL, NOTIMP and REFUSED advance the server cursor before considering TC. A NOERROR reply with no answers, AA, RA or additional records also advances it. Other responses request TCP when TC is set and truncation is not explicitly ignored; otherwise they remain responses. NXDOMAIN is retained for the search/address layer. Authority-record count alone does not suppress the empty-reply rule.

The server driver now applies this policy to both complete replies and validated truncated headers. Retry continues the existing cursor and total deadline; exhaustion returns the last rejected header, reason and endpoint. Parent abort observed during cleanup stops further attempts. `UseTCP` currently returns the selected server/truncation reply for a subsequent transport orchestrator; it does not yet open a TCP exchange. The low-level query API still returns RCODEs unchanged. The header policy exposes ignore-TC explicitly, while this driver requests normal TCP fallback behavior. Full resolver-option wiring, EDNS extended status/negotiation and actual TCP fallback remain unfinished.

Eight generic laws specify failure precedence across arbitrary empty/truncation/ignore inputs, empty-success rejection, independence of other statuses from the empty heuristic, TCP selection, explicit ignore-TC acceptance and consistent handling of useful successful replies. Header bit extraction and numeric RCODE decoding are covered by compiled differential cases, not claimed as universally proved.

## Executing the UDP-to-TCP switch

`dns-transport.exchangeRequest` now drives UDP attempts and executes TCP fallback through the existing TCP recovery/server owners. The same immutable request and borrowed total-deadline signal span both transports. UDP attempt cleanup finishes before the first TCP connect. Ordinary UDP answers return immediately; accepted truncation switches to TCP at the exact current server entry, then may advance through only the remaining suffix of that selected pass. There is no UDP restart, later retry round or search for a matching endpoint value that could confuse duplicates.

`dns-udp-schedule.fallback` supplies the selected entry plus that suffix. Its generic law holds for arbitrary selected values, original lists, remaining lists and later-round counts. The TCP owner preserves its existing one-reset recovery at length-prefix reads and stops on terminal abort/cleanup errors. TCP response codes and TCP truncation remain returned responses, without reapplying UDP failover policy. The transport result preserves either the UDP failure report or TCP failure/cleanup report as typed alternatives. Successful UDP messages are converted into the common TCP query reply representation without re-parsing or JSON conversion.

The live combined fixture checks exact wire bytes, visit order and lifetime boundaries. It currently requires the isolated compiler cache/GC experiment to build within the 8 GiB guard; this is documented in the Bend issue log and validation records. No compiler/runtime patch was installed. Initial forced-TCP selection, oversized-query transport selection, EDNS negotiation and adoption into the system resolver remain separate integration work.

## Initial transport selection

`dns-transport-choice.prepare` checks the complete request encoding, then chooses TCP when explicitly forced or when the encoded query exceeds 512 bytes. EDNS option bytes count toward this threshold; the advertised response payload size does not replace it. The cutoff follows the [pinned send implementation](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/res_send.c) and [packet-size definition](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/arpa/nameser.h). Exact-boundary queries remain eligible for UDP. The bounded size inspection reads at most 513 list cells after validation.

`dns-transport.exchangeWith` applies that choice before network activity. TCP starts with one pass through the selected order and borrows the original total-deadline signal. The default `exchangeRequest` chooses automatically. Zero configured attempts return without opening either transport. Encoding errors are now reported directly by the transport layer before any connection, including forced TCP; UDP's lower-level error API remains unchanged. `dns-query.encode` holds the shared encoder, with the existing UDP entry point delegating to it.

Generic laws cover forced selection, empty input, rejection of encoding errors and the exact length boundary for arbitrary prefixes/suffixes. Live tests send validated queries of exactly 512 and 513 bytes and observe UDP versus initial TCP respectively. System configuration still needs to wire `UseTcp` into the explicit forced argument; EDNS negotiation and live configured-resolver adoption remain pending.

## EDNS-aware UDP disposition

The existing `dns-edns-response` decoder already validates placement, uniqueness, root owner and bounded option data, and address-answer processing already uses its extended status. UDP disposition now reuses it before deciding whether a complete reply should advance the server cursor. Extended codes are interpreted as complete codes: for example, 18 remains an extended error response instead of triggering the SERVFAIL retry associated with low code 2. Malformed OPT records return a typed `InvalidExtension` report and stop, preserving the selected server and deadline diagnostic.

Unknown version/flag/option metadata remains preserved by the decoder; it is not treated as malformed merely because it is unfamiliar. This follows the extension model in [RFC 6891](https://www.rfc-editor.org/rfc/rfc6891.html). A validated truncated reply has only a header available, so that path retains header-only disposition until TCP obtains a complete message. The low-level UDP query API still exposes matched wire replies independently of this resolver policy. EDNS downgrade/negotiation and configured-resolver integration remain unfinished.

## EDNS downgrade scope correction

Inspection of the pinned [glibc 2.39 query path](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/res_query.c) confirms that its request construction/send/error handling does not perform an automatic retry with OPT removed. Its construction retry handles buffer sizing, not an EDNS response failure. RFC 6891 makes downgrade optional and excludes it when required options would be lost. Earlier milestone notes listed “EDNS negotiation” as unfinished without establishing that obligation from the parity target. No automatic downgrade state machine is required for this target: retain explicit request options and return the validated response/error. Configured-resolver adoption remains the next integration step; optional future downgrade would need an explicit policy rather than silently changing request intent.

## Configured transport in address lookup

`resolver-transport.prepare` retains the full parsed options alongside server entries timed in original configuration order. Rotation therefore moves entries with their original budgets instead of recomputing positions. `dns-exchange-source` borrows either the established TCP selector or a configured selector of timed numeric endpoints. The configured branch supplies `UseTcp` and the configured attempt count to `dns-transport.exchangeWith` under the existing total-deadline signal.

`dns-address-lookup.exchangeTransportOptionsWith` accepts this source while sharing the existing alias history, fresh-ID generation, answer selection and cancellation checks. Selection happens after the ID draw and retained-abort check, once per question; retries reuse that selected order and request, while alias follow-ups draw a new ID and select again. The existing public TCP entry points retain their signatures and error mapping. Configured transport failures and retained aborts have explicit typed alternatives.

The loopback fixture exercises both address families and A/AAAA queries through native one/four-thread and Bun backends. It checks alias follow-ups/loops, rotation, retry ID reuse, UDP-to-TCP fallback, forced TCP, EDNS bytes, empty/NXDOMAIN answers, invalid inputs, entropy failure and total deadline cleanup. A directly retained child abort after the ID draw prevents selection and network activity. Aborting the parent during the draw has an asynchronous forwarding race: the first selection/send may already occur, but cancellation must settle without further attempts and all owned resources must close. This does not promise packet nondelivery.

This milestone integrates transport into address lookup, not the complete configured resolver. The system loader and search/resolver owner still construct the explicit TCP path; migrating them and classifying native transport failures for search remain pending. The shared lookup import now needs the isolated candidate's UDP primitives even when testing TCP. Compiler cache/GC experiments remain uninstalled and have no general performance approval.

## Search over configured transport

`dns-address-search.searchTransportOptionsWith` now borrows the generalized source. Search candidates and alias follow-ups share one total deadline and rotation owner. The existing TCP convenience entry points wrap their selectors in `TcpSource`; request generation, alias handling and search progression stay shared.

The completion adapter classifies exhausted native transport reports before passing them to the existing search policy. UDP SERVFAIL rejection retains the distinct server-failure cause, allowing another suffix. Other exhausted UDP response rejections and local attempt expiry become temporary failure, which ends suffix expansion but permits the final direct-name candidate when applicable. This follows the single-query send failure and search handling in the pinned [glibc query path](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/res_query.c). An exhausted NOTIMP/REFUSED transport rejection is therefore different from an accepted TCP response with that code. Socket errors use the existing platform refusal predicate, not hard-coded errno numbers.

Parent/default aborts observed when retiring a UDP attempt prevent search continuation, even if the primary failure would otherwise allow it. Malformed EDNS, validation, entropy and other terminal failures keep their complete typed errors. Forced/fallback TCP uses the same network-failure classifier as explicit TCP, and only cleanly retired exchanges can enter search precedence. Stream cleanup failures retain the original report and halt.

The new generic laws prove immediate termination of the pure received-outcome transition for arbitrary answer/failure values, search origins, histories and cursors, plus initial-failure precedence over arbitrary later history. They do not prove the effectful driver terminates or that resource cleanup succeeds. Those properties remain checked by live integration. The system loader and persistent configured resolver owner still need migration; this entry point does not change the default system resolver.

## Persistent configured resolver ownership

`resolver-configuration.Config<Server>` assembles timed entries, full resolver options, domain diagnostics, the caller's total deadline and read limit into one immutable value. Server values are generic so configuration laws do not depend on socket IO. Options live only in the transport preparation; search/request projections use those same options. Preparation rejects an invalid server-count/timeout plan before exposing a configuration.

`dns-resolver` specializes that value to numeric socket endpoints. Its owner holds the generic selector, while borrowed resolver snapshots share immutable settings and rotation state. Creation seeds rotation through the existing injectable uniform-index source when enabled; disabled rotation needs no entropy. `lookupWith` supplies the configured source to native search, preserving one deadline across candidates, aliases, retries and fallback. Repeated calls retain rotation but each owns its own total deadline.

Replacement constructs the next owner first. If seeding fails, it returns the typed error and still-usable previous owner, including its selector position and configuration. On success it closes the previous selector after construction. All borrowed lookups must settle before replacement or close; snapshots do not make use-after-close valid. Explicit TCP ownership remains available separately.

Generic laws specify complete configuration assembly, transport-error preservation and common search/transport settings for arbitrary server types and values. They do not establish IO lifetime or randomness. Live owner/search and replacement fixtures check those integrations. System configuration loading still produces the explicit TCP configuration and remains the next migration boundary; this owner is not yet selected by the default system loader.

## System configuration to native owner

`resolver-system-config.loadWith` now returns `resolver-configuration.Config<Endpoint>` in `Prepared.resolver`, ready for `dns-resolver.create`/`createWith`. It converts resolved server entries without dropping numeric addresses, ports, IPv6 scope IDs, duplicate occurrences or configured order. Strict option acceptance precedes transport-plan preparation. A plan error returns `InvalidTransport` with the complete source report; option and IO loading errors retain their existing typed forms. Successful preparation retains the source report and search configuration alongside the native settings and allocates no owner until explicitly requested.

The transport preparation's one-to-three-server boundary now applies to system configuration: more than three entries are rejected rather than silently truncated. Missing/unreadable configuration defaults and source diagnostics retain their established policy. The loader fixture checks actual temporary-file/environment/interface handling, one/two/three-server timing, retry and feature retention, four-server rejection, source diagnostics and creation/closure of an owner for accepted results. It does not send DNS packets; the preceding owner/search suite supplies network evidence. The prototype CLI and HTTP hostname-resolution path have not been migrated by this change.
