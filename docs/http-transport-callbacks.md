# Reusable HTTP transport operations

The response and bounded-body loops accept borrowed `http-transport-callbacks.Read` and `Close` handles. These are `Data` callback handles backed by the existing native callback factory. Each invocation obtains a fresh affine closure, releases the factory lock before calling user code, and transfers the affine transport state through the call. The loops never copy a function value.

`Response.start` and `Response.next`, `Consume.bytesUsing`/`textUsing`/`jsonUsing`, and `Provider.accept` expose this runtime-injectable interface. Their caller owns the callback factories and must keep them alive until every call has returned. The returned response body owns the transport state; it does not silently own or retain these operation handles. The callback owner disposes both factories after its last operation.

The existing `startWith`, `nextWith`, consumption `*With`, and provider `acceptWith` conveniences now take compile-time transport types and operations. Each wrapper creates two factories, borrows them for the complete operation, and disposes them before returning. `Response.closeWith` retains its ordinary affine function parameter because early close invokes it at most once. Static wrappers specialize operation code, but do not permit an arbitrary captured runtime closure to masquerade as reusable. Callers needing runtime captures use the borrowed-handle interface. This introduces explicit factory allocation in the static wrappers; it is not a claim of zero overhead or measured throughput equivalence.

This corrects BEND-024 in the application: `http-response.seek`, `http-response.drive` and `http-body-consume.drive` previously copied affine functions under `@unsafe`. Their remaining unsafe annotations concern unbounded external IO progress. No compiler change relaxes affine ownership, and no new unsafe definition is added. The reduced intentionally invalid example remains useful evidence of the checker/backend hazard; the production loops no longer depend on that behavior.

The provider status laws retain their generic scope by quantifying over callback handles. The concrete fetch boundary takes an affine header-acquisition function once; its three failure-path laws now quantify over any such function and prove it is bypassed on earlier failures. Typed errors, cleanup ordering, unread successful response transfer and retry policy are preserved.

Validation combines the full generic proof/mutation gate, the existing response, buffered-body and provider-status trace suites, a new captured-callback variant with separate mutable read/close counters, the composed request/retry fixture and live socket/SSE regressions. The counters verify exact invocation counts; test-only runtime audits check callback/channel and IO retirement. Python orchestrates fixtures and checks traces; it supplies no production transport behavior. [The runtime record](runtime-validation/2026-09-21-http-transport-callbacks.json) contains 3,069 passing cases with source/program hashes. The full proof gate passes 390 public laws and 65 supporting lemmas and rejects 216 type-correct mutations, open obligations and a missing proof; see [proof evidence](proof-validation/2026-09-21-http-transport-callbacks.json).
