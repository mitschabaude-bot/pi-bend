# Owned native Responses acquisition

`openai-responses-owned-acquire.run` composes the existing preparation program, payload/response hook policy, retry loop and system runtime. Preparation, retry-option validation, payload selection, envelope validation/serialization and cancellation inspection happen before system configuration is read. A request rejected at these boundaries never initializes a resolver, fetch callback or retry runtime.

The immutable payload plan retains the original `Preparation.Prepared`. Its validated wire form contains the serialized request, response hook and resolved retry options. Each retry uses that same wire value; the payload hook runs once. Original grammar metadata survives numeric or null payload replacement independently of the outgoing body. No mutable ownership cell or JavaScript object semantics are involved.

A successful result transfers the system runtime and prepared response as one affine owner. Acquisition failure retires the runtime before returning the typed cause. Response-hook failure first closes the response using the existing hook driver, then retires the runtime. `release` closes a successful response before its runtime, even when response closure returns a failure. Initialization errors and acquisition errors remain distinct typed variants.

The pinned upstream provider retry wrapper gives cancellation precedence after any failed attempt, including an invalid URL. The installed OpenAI SDK also checks cancellation after request construction and before fetch. `tests/openai_owned_order_reference.mts` executes these cases against those sources without network access. Bend follows that ordering while applying the previously accepted stricter validation rules. Cancellation can still arrive during initialization or transport; the lower native fetch path continues to observe the same parent signal.

Six generic request-plan laws establish successful transfer of the complete original preparation, request, response callback and retry options; typed payload/envelope failures; preservation of other request options when removing the payload hook; and cancellation precedence. Their standalone proof record is `docs/proof-validation/2026-09-21-responses-payload-plan-standalone.json`. The generic lazy-owner laws separately establish preparation/initialization short-circuiting and cleanup order. The [completed root gate](proof-validation/2026-09-21-owned-provider.json) includes these and the previously standalone default/system-owner laws: 502 public laws, 74 supporting lemmas, and 268 well-typed mutations rejected.

The [integration fixture](runtime-validation/2026-09-21-owned-acquire.json) passes 90 executions: fifteen cases on native one/four threads and Bun, both plain and audited. Early failure/cancellation cases point configuration at a blocking FIFO: returning proves that configuration was not opened. Other cases exercise actual system-owner creation, numeric/hosts-file resolution, payload replacement, a 503 retry, response-hook rejection and closing an incomplete response body. Original hooks remain callable afterward. Audited channels, parked IO, sockets, timers and fixture file descriptors finish at zero. The fixture injects a prepared value at this acquisition boundary; the separate provider-core suite covers real transcript/credential preparation. Retaining grammar metadata here is not a second claim of stream-processing coverage.

This module is the owned **cleartext** acquisition path. Full system-owned provider-session assembly has separate verification in progress. Default SSE hooks/error rendering/clock, custom-fetch dispatch, TLS and authentication lifecycle still need installation in the complete public provider. No upstream suite is promoted by this integration alone.
