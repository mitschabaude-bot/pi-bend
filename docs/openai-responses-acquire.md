# Responses acquisition

`api/openai-responses-acquire.bend` connects the prepared client settings and payload to the existing provider hook/retry driver. Its borrowed attempt callback receives a fully serialized `Envelope.Request` and returns the canonical affine HTTP response. Native and custom transport adapters can share this boundary. The caller supplies its structured error domain and embeds envelope errors into it; the bridge does not flatten errors or assume arbitrary custom transport failures are retryable.

The ordering follows pinned `pi-mono/packages/ai/src/api/openai-responses.ts`: prepare parameters, call `onPayload` once, keep any explicit replacement, retry requests with that selected payload, call `onResponse` once on successful acquisition, then transfer the body to the provider driver. `provider-request` already implements this ordering and releases a successful body if its response hook fails. The new layer uses that driver rather than implementing a second hook or retry loop. Serialization remains inside each request attempt, matching SDK request construction after hook selection. The SDK retry-count header stays zero because pi's outer retry helper owns retries. Explicit null and zero replacements retain the envelope layer's approved present-value serialization, instead of reproducing the SDK's falsy-body omission. Nonfinite JSON replacements are rejected before transport.

`Client` holds URL context, native client defaults, credentials, client headers, base URL and timeout. `prepared` projects these settings and the payload from the existing `Preparation.Prepared`; compatibility, grammar and cache information remain available in the caller's immutable prepared value for subsequent stream processing. `run` owns only its temporary payload-to-envelope callback. Supplied hooks, attempt callback and retry effects remain borrowed; a returned response body must not depend on the disposed bridge. The supplied release function owns response cleanup on hook failure.

Three generic laws preserve the prepared client/payload projection, establish the absence of transport effects after any envelope failure, and transfer every successful envelope unchanged to the attempt callback. The existing provider-request laws constrain hook selection and cleanup ordering. Neither set proves arbitrary network progress or compiler correctness. Mutation checks deliberately turn envelope rejection into a retryable provider failure or discard a valid envelope.

`tests/openai-responses-acquire.bend` composes this bridge with the real native cleartext attempt, native fetch, fetch/body deadline scope, retry helper and abortable sleep. A loopback oracle checks the final POST target, authentication/content/retry-count headers, byte length and complete selected JSON body. Payload replacement across retry, zero/null replacement, payload-hook failure, response-hook failure, simultaneous response/cleanup failure and envelope rejection are covered. Cleanup failure is injected after actual release; it is not an OS failure injection. The fixture renders errors as strings for readable traces, independently of the production bridge's generic typed error domain.

TLS, complete authenticated provider/session assembly, content decoding, redirects and the remaining full-port requirements are still unfinished. This acquisition boundary does not promote an upstream suite to complete.

The [full proof gate](proof-validation/2026-09-21-openai-responses-acquire.json) passes 402 public laws and 65 supporting lemmas and rejects 221 well-typed mutations, open obligations and a missing proof. No unsafe declaration was added.

Reproduce by emitting `tests/openai-responses-acquire.bend` to `build/openai-responses-acquire.c` and `.js` with the isolated compiler described in `docs/laws.md`, using `scripts/run-rss-guarded.py` with 32 GiB and 24 GiB guards respectively. Generate the test-only resource instrumentation and compile both native variants with `python3 tests/transport_audit.py build/openai-responses-acquire build/bend-profiles/dns-transport-teles/bend2 --compile`, then run `python3 tests/openai_responses_acquire_check.py`. The harness's `--js-only` option selects a provisional Bun run while native compilation is in progress. Resource checks use the same explicitly bounded native descriptor scan and Bun owner/scheduler counters as the [native attempt fixture](openai-responses-native-attempt.md).

All 72 integration executions pass: 12 scenarios on native one/four threads and Bun, in production and resource-instrumented programs. Every audited residual counter is zero.
