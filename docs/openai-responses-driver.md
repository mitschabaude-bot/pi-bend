# OpenAI Responses outer stream lifecycle

`api/openai-responses-driver.bend` implements the outer request/Start/process/terminal/close sequence from pinned pi's `api/openai-responses.ts`. Acquisition can compose the existing request builder, hooks and retry stage and transfers one affine response owner on success. The driver emits Start before consuming that owner. The processing adapter retires the owner and returns its partial message, primary failure and independent cleanup outcome. A Start-delivery failure releases the unread owner directly.

`api/openai-responses-lifecycle.bend` holds the immutable initial message, terminal classification and failure transformations. After successful processing, cancellation takes precedence over the stop reason; pending output is rejected; stop, length, tool use and deferred output retain their terminal kinds. Existing failures preserve their cause even when cancellation also occurred. Error finalization changes only stopReason and errorMessage, retaining content, usage, response metadata and timestamp. Parser scratch data already lives outside public messages and needs no reflective deletion.

Failures remain tagged native values: acquisition, Start emission, processing, cleanup, terminal delivery, cancellation, missing stop reason and an existing output error. Application-selected `E` can be a typed sum of transport, provider and extension errors. A statically specialized pure formatter supplies presentation without changing those causes. `RunResult` retains the terminal state and separate cleanup/delivery failures. No new unsafe annotation or compiler patch is introduced by either production module.

Every terminal delivery outcome calls the supplied close callback with the final snapshot. If a successful terminal event cannot be delivered, the run becomes a typed delivery failure. An existing primary failure survives a second delivery failure. The driver does not repeatedly call a failing sink. The canonical event-stream integration settles the final result through `end(Some{message})` when delivery failed before publication. This does not promise to retract effects that an arbitrary sink already committed before returning failure; sink/close handles remain borrowed and their implementations must honor their publication and lifetime contracts.

## Correctness evidence

Fifteen generic laws specify cancellation precedence, exhaustive successful terminal-kind boundaries, pending rejection, preservation of unrelated fields, last-write behavior of failure updates, primary/cleanup precedence, retained terminal messages and close-before-return as an IO-program equality. The [gate](proof-validation/2026-09-21-openai-responses-lifecycle.json) checks 283 public laws and 59 supporting lemmas and rejects 163 well-typed mutations. The six new mutations ignore cancellation, erase partial content, hide primary failures, turn failed delivery into success, skip closure or replace the terminal reason. These laws do not prove termination of arbitrary callbacks or correctness of the compiler/runtime.

The [integration record](runtime-validation/2026-09-21-openai-provider-driver.json) covers nineteen scenarios on native one/four threads and Bun, each with production and resource-audited builds: 114 executions. The fixture composes canonical request hooks/retries, actual HTTP request upload and status handling, owned SSE/JSON reading, the existing Responses content processor, and the canonical assistant event stream. A stream iterator and final-result waiter run concurrently with the driver. Retained events are inspected after the run to check immutable snapshots. Peers verify request payloads and connection retirement; an unread response may close with TCP reset rather than EOF. Native audits cover live channels, parked IO and socket descriptors 0–4095; Bun audits channels and live/waiting IO.

The oracle executes the actual pinned block from payload selection through catch/end, together with the actual content processor. The client, initial message/timestamp and retry effects are supplied by the fixture. It covers successful content/usage, HTTP failure, payload/response hook failures, Start/content/terminal sink failures, cancellation after processing, missing terminal response, malformed JSON, independent/combined cleanup failures, exhausted/successful retries, explicit null replacement, provider failure, pending output and length termination. Test adapters select string presentation for internal typed causes; they do not replace production transport or parsing.

Declared adaptations are retained beside the reference results. Hook/Start failures retire the unread native response. An error-emission failure closes and settles the stream instead of leaving the upstream async function rejected and unfinished. A failed Done delivery closes with a typed failure without making another sink attempt. Cleanup outcomes are retained independently. The fixture's abort hook explicitly aborts its supplied parent signal, and its oracle mirrors that injected choice; this is not a claim that the OpenAI SDK aborts a user's signal. Oracle snapshots are cloned at emission to model the previously approved immutable-event policy.

## Remaining provider assembly

This is an owned execution driver, not yet the complete public asynchronous `stream` entry point. Production creation/ownership of the canonical event stream, concrete request serialization and headers, full typed HTTP-error presentation, authentication/TLS and provider dispatch still need assembly around these components. The HTTP integration uses a test payload to exercise upload and hooks; it does not claim a live model request. Other providers, full coding-agent/TUI parity and the original provider suites remain incomplete. No upstream suite status is promoted by this milestone.
