# Paired DNS response classification

`dns-pair-result` merges two classified reports for one candidate name. Each classification retains the original report, separate from whether it contains usable addresses, a valid negative reply, an unavailable response or a terminal failure. The report type is generic; the native adapter stores the complete `Result<Lookup.Error<Reason>, Answer.Selection>`. Address lists, per-family canonical names, TTLs and native errors are not flattened or replaced.

A terminal failure prevents success even if its sibling has addresses. This retains the existing strict treatment of malformed data, cancellation, entropy failure and cleanup failure. Otherwise, either usable answer succeeds. Both successful and terminal outcomes preserve both original classified reports in IPv4/IPv6 order. Ordinary negative results produce the cause needed by the search cursor; they are not claims of cacheable negative DNS answers.

A valid reply takes precedence over an unavailable sibling. When two valid replies contain no addresses, the first nonzero response code determines the cause; two NOERROR replies mean no data. NXDOMAIN maps to missing, SERVFAIL to server failure, and other nonzero codes to unrecoverable. Two unavailable responses use the first one's existing classified cause. This is a pure merge kernel, not a replacement for response validation or transport retry policy.

The caller must pass `IPv4First` or `IPv6First` explicitly. No integration default has been selected. The pinned [glibc query layer](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/res_query.c) chooses the first buffer's nonzero code, falling back to the other buffer's code when it is NOERROR. The [UDP send layer](https://raw.githubusercontent.com/bminor/glibc/glibc-2.39/resolv/res_send.c) fills reply buffers in arrival order, so this is not inherently IPv4-first precedence. The user has been asked whether to replace that incidental timing dependence with deterministic family precedence. Both choices can use this kernel; collecting the appropriate order and choosing the application default remain pending.

`dns-pair-classify.classify` first uses the existing native search classifier, preserving its cancellation, cleanup and platform socket-error decisions. It then recovers the exact response code for accepted negative DNS replies and represents valid empty selections as NOERROR. Exhausted UDP rejection reports remain unavailable according to transport policy: they are not silently promoted to accepted replies. Their original headers, rejection reasons and retained deadline state stay in the full report. A late attempt-expiry diagnostic does not erase a completed failure classification, while retained parent/default aborts remain terminal.

## Evidence and limits

Seven new generic laws cover retention of both arbitrary reports under either priority for terminal and representative successful combinations, empty-reply deferral, reply precedence over unavailability, and stability of identical unavailable causes. The full proof gate checks 142 public laws and 55 supporting lemmas and rejects 98 typed mutations. These laws do not prove every native error classifier or OS errno behavior.

All 6,144 executed pairs pass across native one/four threads and Bun, covering both explicit priority orders, usable IPv4/IPv6 selections, empty replies, ordinary and extended response codes, exhausted UDP rejection variants, attempt expiry, retained parent/default aborts, socket refusal/other socket errors, TCP EOF, cleanup failures, entropy failure and invalid lookup state. They construct complete typed reports and exercise the native classifier and pure merge. They do not issue network requests or establish equivalence with libc's complete paired transport state machine.

The fixture initially hit the known literal-string pattern expansion cliff. Replacing only CLI-tag dispatch with string equality and native enum dispatch retained every case and reduced native emission from 38.6 to 3.2 seconds, sampled group peak RSS from 5,939,144 to 950,096 KiB, and generated C from 39,495,917 to 648,744 bytes in this controlled comparison. The same isolated compiler candidate was used before and after; these are individual observations, not a universal performance guarantee. No compiler patch was made. Both sources, complete validation records and output fingerprints are retained in the [investigation record](bend-issues/2026-09-20-dns-pair-pattern.json).

At this classification milestone, shared paired transport, identifier/server selection, receipt-order metadata, deadline integration, family-related options and adoption into the native resolver remained unfinished; the next section records the implemented exchange layer. The new merge kernel does not change the current single-family resolver or the application default while the precedence choice is pending. [Proof evidence](proof-validation/2026-09-20-dns-pair-result.json) and [runtime evidence](runtime-validation/2026-09-20-dns-pair-result.json) retain verified source hashes. Runtime builds use the existing uninstalled compiler candidate under the 8 GiB guard; no runtime/compiler patch or new unsafe annotation was added.

## Live paired exchange

`dns-address-pair.exchangeWith` now executes one candidate's A and AAAA questions concurrently. It borrows one total-deadline signal and returns complete reports in family order only after both operations have settled and their child channels have closed. Setup failures are a separate typed result: an unstarted sibling never receives a fabricated lookup error. Merging and advancing the search cursor remain external.

`dns-pair-setup` rejects zero read size and absent servers before effects, observes retained cancellation before each identifier draw and after the second successful draw, validates both full request encodings, then commits one server-order selection. Both queries and their alias follow-ups use that immutable snapshot. Cancellation observation and rotation are not atomic; cancellation arriving after the last check can consume that rotation step. Entropy or encoding failure before selection cannot consume it. Encoding validation follows both successful draws, so malformed names/options or out-of-range identifiers can consume two draws without sending any packets.

The initial identifiers are reserved in family order. `dns-address-lookup.exchangeRequestWith` uses the supplied identifier for the first question and draws fresh identifiers only for alias follow-ups. It explicitly rejects non-IN classes. Repeated identifiers are valid here because each query owns a separate socket/connection and validates its question; uniqueness across the pair is not assumed. Per-query retries and UDP-to-TCP fallback retain their existing ownership. This is not glibc's shared-socket dual-query transport, and `single-request`/related family options are not implemented by this API.

The [live exchange evidence](runtime-validation/2026-09-20-dns-address-pair.json) covers 150 cases across IPv4/IPv6 transport and native one/four threads plus Bun. The server withholds initial replies until both questions arrive, enforcing concurrent startup without a sleep. Cases cover completion order, equal identifiers, rotation/fixed order, independent aliases, fallback, forced TCP, EDNS, negative/empty replies, shared-deadline expiry, cancellation and setup failures. Native operation/timer/channel/socket/connection/parked counters and Bun explicit channel closure plus live/wait audits return to zero; native descriptor inspection is bounded to 0–4095. All 276 [existing owner/search regressions](runtime-validation/2026-09-20-dns-pair-owned-regression.json) also pass.

Four new generic laws describe shared query intent, family-tagged encoding failure precedence and preservation of arbitrary requests whose actual encodings succeed. The [proof gate](proof-validation/2026-09-20-dns-pair-queries.json) now checks 146 public laws and 55 supporting lemmas, rejecting all 101 typed mutations. These proofs do not establish IO scheduling or resource lifetime; the live fixtures check those separately. Source hashes were verified before archiving. IO builds still use the existing uninstalled compiler candidate under the 8 GiB guard; no compiler patch or unsafe annotation was added.

At the exchange milestone, shared search integration remained pending; the following section records that integration. Receipt-order metadata, family-related resolver options and application adoption remain pending. The default merge priority is still unset pending the user's answer.

## Paired candidate search

`dns-pair-search.searchWith` connects the live exchange to the existing finite search cursor. Its explicit inputs include the cursor, request options, borrowed server source, identifier callback, parent abort signal, total time budget and merge priority. Both native queries settle before classification and merging. An ordinary merged negative cause advances that one cursor; neither family can independently move to a different suffix. Successful results retain both complete classified reports, including a negative sibling and independent alias canonical names.

Setup failure becomes a terminal `SetupFailed`; a terminal started-query outcome becomes `QueryFailed` carrying both classified reports. The adapter wraps those outcomes for the existing driver rather than inventing a second retry/search algorithm. The driver's exhausted result retains its existing DNS error class, not an accumulated transcript of every candidate. Zero read size and absent servers reject before allocating a deadline. Otherwise one owned deadline spans every candidate, retry and alias, closes after the driver returns, and contributes its retained reason to the report. The caller's source and parent remain borrowed.

This API still requires an explicit priority. It does not pick a default, add receipt-order metadata or claim support for family-related resolver options. Persistent resolver/hosts entry-point adoption and system configuration wiring remain separate work.

The live fixture exercises both explicit priorities over IPv4/IPv6 transport on native one/four threads and Bun. Candidate wire traces check paired suffix progression, server rotation once per started candidate, reserved identifiers, separate aliases, forced TCP/EDNS, ordinary negative siblings, malformed-record halts, deadline expiry after suffix progression, setup failure on the next candidate, absolute names, exhaustion and invalid setup. A per-candidate reply barrier requires both requests before replying. The priority case uses two accepted TCP negative replies with different response codes and observes the different next candidate under each explicit priority; it does not assume exhausted UDP rejection is an accepted reply.

This layer introduces IO composition and typed outcome wrapping, not a new pure search or merge algorithm. Existing generic cursor/merge/query laws remain applicable; live tests supply scheduling and resource-lifetime evidence. No new universal claim is made about OS IO. The existing 146-law/55-supporting-lemma/101-mutation proof record's entire 138-file source closure was reverified unchanged.

All 168 [live paired searches](runtime-validation/2026-09-20-dns-pair-search.json) pass. Native operation/timer/channel/socket/connection/parked audits and Bun explicit channel closure plus live/wait audits return to zero; native socket inspection remains bounded to descriptors 0–4095. The source hashes match the final files. Builds use the existing uninstalled compiler candidate under an 8 GiB guard; no compiler/runtime patch or unsafe annotation was added.

## Persistent resolver and hosts adapter

`dns-pair-resolver.lookupWith` borrows the existing `dns-resolver.Resolver`, projects request/search policy from its canonical immutable configuration and passes retained transport options, total deadline and read size into paired search. It shares the owner's rotation state across calls; it introduces no second configuration store or owner. The owner must outlive every borrowed lookup, as with the existing single-family API.

`dns-pair-hosts-resolver.lookupWith` uses the shared `hosts-resolve.resolveWith` dispatcher with `Any` family selection. Local rows retain source order, aliases and duplicate occurrences. A hit containing only one family still satisfies this files-first operation; DNS does not fill in the missing family. Source failures remain terminal. Only a complete local miss parses the DNS presentation name and invokes paired lookup. Locally valid tokens that are invalid DNS presentation syntax can therefore resolve from hosts, while an invalid DNS name on a miss returns a typed parse failure without identifier draws or rotation.

Both adapters keep priority explicit and return complete typed reports. Existing single-family entry points remain available. System source loading/reloading, numeric-host short-circuiting, IDNA integration, remaining family-related resolver options and HTTP adoption are still pending; these modules are not a claim of complete system hostname resolution.

All 240 [live adapter cases](runtime-validation/2026-09-20-dns-pair-hosts-resolver.json) pass on native one/four threads and Bun over IPv4/IPv6 transport and both explicit priorities. The suite reruns paired search scenarios through canonical resolver configuration and hosts dispatch, then checks mixed/single-family local hits, duplicate preservation, malformed source data, invalid DNS presentation names and repeated calls using one owner. Local outcomes and parse failures consume no query identifiers or rotation; repeated network calls advance the persistent selector. Native and Bun resource audits return to zero with the same scope as the paired-search fixture. All archived source hashes match. Existing proof and paired-search validation closures remain unchanged. Builds use the existing isolated compiler candidate under the 8 GiB guard; no compiler/runtime patch or unsafe annotation was added.
