# Native OpenAI request headers

`utils/provider-header-state.bend` stores normalized header settings in one immutable record. A null setting means an explicit removal, while a missing setting means no decision. Later layers replace earlier settings case-insensitively. HTTP header normalization validates names and values; the first failure is retained. Materialization omits removal commands only after policies have inspected them. This avoids separate mutable header and deletion collections while preserving the meaning of the SDK's nullable headers.

`api/openai-request-headers.bend` composes defaults/platform fields, bearer credentials, client defaults, serializer headers and request overrides in the OpenAI SDK's order. It preserves organization/project overrides, normalized empty values, explicit removals and typed header failures. Authentication validation accepts a nonempty authorization/API-key header or an explicit removal of either, as the SDK does. Reintroducing an empty value clears the removal marker and can make validation fail. This is client configuration validation; it does not establish that a remote service will authorize the request.

Timeout preparation uses the SDK's 600,000 ms default, rejects fractional/nonfinite or negative values, preserves zero, and derives `X-Stainless-Timeout` by truncating milliseconds divided by 1,000. Zero omits that header. Retry count is caller-supplied; pi disables SDK retries and supplies zero. Native platform/user-agent metadata is injected explicitly rather than pretending Bend is JavaScript/Node. Process environment acquisition, platform detection, scheduling a timeout, body serialization and the full transport/session entry point remain separate integration work.

## Correctness evidence

Fourteen header-state laws cover layer/entry composition, singleton application, first-error preservation, replacement, explicit removal, clearing removal through assignment and materialization. Ten request-header laws cover explicit timeout retention, invalid timeout rejection, typed errors, authentication acceptance/rejection, removal overrides and interchangeability of the two authentication header methods. These quantify over arbitrary settings, fields, names, values and relevant errors; the absence of both credentials is an empty-input boundary. Two supporting lemmas prove disjunction symmetry and the empty-entry identity. Materialization assumes states constructed through checked inputs; the laws do not turn arbitrary directly constructed state records into validated HTTP fields.

The [proof record](proof-validation/2026-09-21-openai-request-headers.json) checks 329 public laws and 61 supporting lemmas and rejects 189 well-typed mutations. The existing unsafe import audit is unchanged. Direct application/value contracts precede composition proofs, so the new mutations reject through the intended violated contract rather than first reporting an invalidated composition proof.

The [SDK comparison record](runtime-validation/2026-09-21-openai-request-headers.json) contains 399 cases on native one/four threads and Bun, totaling 1,197 comparisons. The oracle executes SDK 6.40.0's actual header construction, bearer-header construction, authentication validation and positive-integer validator. Platform identity is injected at its explicit boundary. Cases include all combinations of retaining/removing/reintroducing authorization and API-key fields, client/body/request precedence, absent/default/zero/fractional/negative/large timeouts, organization/project fields, Unicode byte values and invalid HTTP names/values. Error families are compared; raw SDK diagnostics are retained alongside the typed native errors' definitions. No network requests or real credentials are involved. ## Request-envelope integration

The standalone `build` helper resolves its missing timeout to 600,000 ms before deriving a header, and its isolated SDK harness supplies that effective value explicitly. This is not the entire SDK `buildRequest` boundary: the SDK passes the original, possibly omitted timeout to header construction while returning an effective timeout separately. [The Responses envelope](openai-responses-envelope.md) therefore validates the effective timeout and calls the staged `layered` operation using the original timeout specification. An omitted timeout yields a 600,000 ms request timeout with no `X-Stainless-Timeout` header. Integrated actual-SDK cases cover this distinction, including explicit zero and explicit 600,000 ms.
