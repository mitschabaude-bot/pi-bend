# Typed HTTP host resolution

`http-url.Endpoint` already retains `url-host.Host`. `http-host-route` consumes that value directly: an IPv4 or IPv6 variant yields the exact shared connection address, and a nonempty domain yields its unchanged name for lookup. Empty and opaque host variants fail as invalid HTTP hosts. URL IPv6 values have scope zero; scoped numeric destination strings use the separate numeric scope API. This layer does not serialize, reinterpret, normalize or parse host text again. Existing URL parsing determines the typed value, including its URL-specific numeric normalization.

The generic effectful dispatcher calls its injected name resolver only for a domain plan and wraps its entire report without flattening failures or metadata. `http-host-resolver` supplies the concrete paired hosts/DNS adapter using a borrowed persistent resolver, parent abort signal, explicit merge priority and already loaded hosts result. Numeric variants bypass that callback even if the hosts snapshot is a failure. Domain variants retain source errors, local rows, invalid-name results and complete paired network reports with their existing provenance.

The pure route and generic dispatcher require no resolver owner. The concrete adapter accepts one already borrowed by its caller; lazy resolver/configuration loading belongs to the higher HTTP client owner. Port, TLS/plaintext choice, HTTP authority and request target remain in the existing endpoint rather than being inferred from resolution results.

Six generic laws establish numeric routing with exact address retention, domain spelling retention and invalid-host boundaries. They describe the routing plan, not OS scheduling or DNS correctness. Live integration checks supply the latter composition evidence while reusing the existing native DNS tests. Address extraction/selection from named reports, connection attempts, TLS, proxy policy and attachment to the full HTTP request driver remain pending. This is a typed resolution layer, not a completed HTTP client or pi port.

All 312 [live routing cases](runtime-validation/2026-09-20-http-host-resolver.json) pass over IPv4/IPv6 transport and both explicit priorities on native one/four threads and Bun. They cover existing hosts/DNS behavior, repeated owner use, and numeric/invalid host variants paired with failed hosts snapshots. Numeric and invalid variants produce no query traffic, identifier draws or rotation. Resource audits return to zero, including Bun explicit channel closure; native socket inspection is bounded to descriptors 0–4095. The [proof gate](proof-validation/2026-09-20-http-host-route.json) checks 164 public laws and 55 supporting lemmas, rejecting all 110 typed mutations. Source and compiler hashes are archived. The existing isolated compiler candidate remains required and uninstalled; no compiler/runtime patch or unsafe annotation was added.

## Connection candidate projection

`http-addresses.prepare` projects a completed resolution into `connection-addresses.Plan`, retaining the complete original result in both available and unavailable outcomes. Numeric results supply one address. Hosts rows supply one ordered sequence without removing duplicate occurrences. Successful paired DNS results supply separate IPv4/IPv6 candidate lists, preserving each family's answer order; only selections classified as usable answers contribute addresses. A failed or halted search supplies no candidates, even when its retained report contains a successful sibling.

The projection adds no family preference, sorting, deduplication, mapped-address conversion or socket activity. Each unscoped hosts/DNS IPv6 address receives scope zero. TTLs, canonical names, aliases, negative sibling reports and deadline diagnostics remain in the retained original value rather than being invented on connection addresses. Address conversion uses the existing native address values directly.

Ordered candidates are nonempty; the paired constructor returns an unavailable plan when both lists are empty. The connection scheduler must still choose how to order/interleave the family lists and handle connection failures before the HTTP exchange can start. Those decisions are independent of DNS error-merge priority.

The candidate core has inductive concatenation and count-preservation laws for hosts and DNS lists, exact address-conversion laws for arbitrary canonical/alias/TTL metadata, and generic report/list-retention laws for ordered, paired and empty plans. Count preservation matters independently: an always-empty conversion can satisfy the concatenation equation but cannot preserve nonempty input counts. Deliberate address-erasure mutations check that invariant directly. Runtime integration checks preserve the old resolution output beside the new projection, making lost diagnostics or changed canonical/TTL values observable.

All 312 [live projection cases](runtime-validation/2026-09-20-http-addresses.json) pass on native one/four threads and Bun. Every case checks both the retained resolution output and projected candidate lists, including duplicates, partial success, independent alias names, numeric literals and unavailable/terminal outcomes. Resource audits return to zero. Thirteen new laws bring the [proof gate](proof-validation/2026-09-20-connection-addresses.json) to 177 public laws and 55 supporting lemmas; all 115 typed mutations are rejected, including erased host/DNS lists checked by the count laws. Source hashes match the archived evidence. Builds and proofs use the existing isolated compiler candidate; no compiler/runtime patch or unsafe annotation was added.
