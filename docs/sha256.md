# Native cryptographic primitives

`packages/runtime/src/sha256.bend` implements byte-oriented SHA-256 in pure Bend, following [FIPS 180-4](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf). `create`, `update` and `finish` provide immutable streaming state; `digest` hashes a complete byte list and `toBytes` returns the 32-byte digest. Updates reject values above 255 and message-length overflow. Construct states through the API; validation does not cover every forged internal state.

The universal `chunk_composition` law proves that arbitrary chunk boundaries preserve the complete state and first error. Its structural proof is registered in the root proof suite, which passes. This establishes streaming composition, not formal equivalence of the compression algorithm to the standard.

The differential harness `tests/sha256_check.py` passed 355 cases each on native one-thread, native four-thread and Bun execution: standard vectors including one million `a` bytes, padding boundaries, random inputs and partitions, every split of a 64-byte message, and invalid bytes. It compares against Python hashlib; Python supplies no production behavior. Recorded results identify the tested sources, generated programs and compiler. The fixture uses the existing tail-recursive string splitter because Bend's standard JavaScript splitter overflows the stack on long input strings.

Build with the project native compiler, then run the harness:

```sh
bun build/bend-native-toolchain/bend2/main.ts tests/sha256.bend -o build/sha256.c -o build/sha256.js
clang -std=c11 -fbracket-depth=2048 -O1 build/sha256.c -lpthread -lm -o build/sha256
python3 tests/sha256_check.py
BEND="$PWD/build/bend-native-toolchain/bend2/main.ts" python3 scripts/check-proofs.py
```

This is a dependency for native TLS. TLS and native HTTPS model requests remain unfinished.

## HMAC-SHA-256

`packages/runtime/src/hmac-sha256.bend` implements [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104) using the same SHA-256 core. `create(key)` prepares immutable inner and outer prefix states, `update(bytes, state)` streams a message, `finish(state)` returns its digest, and `digest(key, bytes)` is the one-shot interface. A prepared state can be reused for multiple messages. Keys longer than 64 bytes are hashed before padding. Invalid key or message bytes return the original offending value through `SHA.Error`.

`tests/hmac_sha256_check.py` checks six full-output [RFC 4231](https://www.rfc-editor.org/rfc/rfc4231) vectors, empty and boundary-length keys/messages, random streaming partitions and invalid bytes against Python HMAC: 343 cases passed on each of native one-thread, native four-thread and Bun execution. The SHA chunk law remains proved; HMAC construction equivalence itself is not formally proved. Build `tests/hmac-sha256.bend` to `build/hmac-sha256.c` and `.js` with the compiler above, compile the C output using the same flags, and run `python3 tests/hmac_sha256_check.py`.

## HKDF-SHA-256

`packages/runtime/src/hkdf-sha256.bend` implements [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869): `extract(salt, input)` returns a SHA digest, `expand(key, info, length)` returns derived bytes, and `derive(salt, input, info, length)` combines both steps. Empty salt supplies the standard unsalted behavior through HMAC's zero padding. Expansion accepts keys of at least 32 bytes and lengths from zero through 8,160 bytes. Prepared HMAC prefix states are reused across blocks. The implementation accumulates blocks in reverse order to avoid repeatedly copying an increasing output prefix.

Errors distinguish short expansion keys, excessive requested lengths, and underlying hash errors. Invalid key and info bytes are rejected even for zero-length output. Expansion checks length before key size, then validates key and info; combined derivation first extracts its key.

`tests/hkdf_sha256_check.py` passed 180 cases on each of native one-thread, native four-thread and Bun execution. It checks all three SHA-256 vectors from RFC 5869, extraction independently, expansion with keys longer than the hash output, padding/block boundaries, zero and maximum output lengths, and rejected inputs. Python `cryptography` supplies an independent HKDF oracle; Python HMAC checks extraction. No formal HKDF-equivalence proof is claimed. Results identify the tested sources and generated programs. Build `tests/hkdf-sha256.bend` to `build/hkdf-sha256.c` and `.js` using the same compiler/flags above, then run `python3 tests/hkdf_sha256_check.py` (requires Python `cryptography`). TLS label encoding and derivation are covered below; handshake, record protection and certificate validation remain unfinished.

## TLS 1.3 SHA-256 derivation

`packages/runtime/src/tls13-kdf.bend` implements the derivation operations from [RFC 8446 sections 4.4.4 and 7](https://www.rfc-editor.org/rfc/rfc8446). `encodeLabel` builds the TLS label, `expandLabel` derives bytes, `deriveSecret` binds a secret to a supplied transcript digest, `advance` performs the derived-salt extraction used for handshake/master secrets, and `finished` computes Finished verify data. Labels are nonempty ASCII strings of at most 249 bytes before the `tls13 ` prefix; contexts are at most 255 bytes. The label encoder supports a 16-bit length; SHA-256 HKDF expansion additionally enforces its 8,160-byte limit.

The caller must supply the correct transcript for each protocol stage, including handshake headers and excluding record headers. The master-secret transition takes 32 zero input bytes. These functions do not constitute a handshake state machine, authenticate a certificate or verify a received Finished message.

`tests/tls13_kdf_check.py` passed 112 cases on each of native one-thread, native four-thread and Bun execution. Twenty expansion vectors are extracted from [RFC 8448 section 3](https://www.rfc-editor.org/rfc/rfc8448); the fixture retains source identity and published handshake messages. Tests reproduce handshake/application secrets, keys and IVs, both extraction transitions, and server/client Finished values from their full transcripts. Boundary and invalid-label/context tests supplement the trace. Python cryptography/HMAC independently checks the reference calculations; no production behavior uses Python. Recorded results identify sources and binaries. Build `tests/tls13-kdf.bend` into `build/tls13-kdf.c` and `.js` with the same compiler/flags above, then run `python3 tests/tls13_kdf_check.py`. These are executed reference checks, not a formal proof of the TLS key schedule. Encryption, key exchange, certificate validation and the handshake state machine remain unfinished.

## AES-128

`packages/runtime/src/aes128.bend` implements AES-128 key expansion and forward block encryption from [FIPS 197](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.197-upd1.pdf). `Block` contains four big-endian 32-bit columns. `fromBytes` accepts exactly 16 byte values and returns `None` for malformed input; `toBytes` serializes a block. `expand` creates a reusable immutable expanded key and `encrypt` encrypts one block. GCM requires the forward cipher for both encryption and decryption; an inverse block cipher is not implemented here.

The substitution operation computes the finite-field inverse and affine transform with fixed-count arithmetic, without secret-indexed lookup tables. This describes the source algorithm, not a verified constant-time guarantee for Bend's generated machine code. No foreign cryptographic implementation supplies production behavior.

`tests/aes128_check.py` passed 532 cases on each of native one-thread, native four-thread and Bun execution. Checks include all eleven round keys from FIPS 197 appendix A.1, known ciphertext vectors, random key/plaintext pairs, every single-bit key and plaintext position, and invalid byte/length rejection. Python cryptography supplies the independent encryption reference. Recorded results identify tested sources and programs. Build `tests/aes128.bend` into `build/aes128.c` and `.js` with the same compiler/flags above, then run `python3 tests/aes128_check.py`. AES-GCM authentication and record protection remain unfinished; raw block encryption is not yet a TLS transport.
