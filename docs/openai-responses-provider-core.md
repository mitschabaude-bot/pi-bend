# Responses provider assembly

`openai-responses-provider-core.streamAt` accepts the canonical model, transcript and Responses options with the caller's hook-error type. It adapts hooks into the provider error domain, selects cancellation once, owns default pricing, and passes real preparation/acquisition into the existing session producer. Transport dependencies, rendering context, timestamp and dependency cleanup remain explicit at this internal boundary. Preparation failures preserve their typed causes and settle the stream without invoking hooks or network.

`openai-responses-prepared-acquire` carries the original preparation together with the successful affine response. Processing obtains grammar mappings from that preparation even when a payload hook replaces outgoing JSON. Its four generic laws establish preparation-failure short-circuiting, successful owner transfer, acquisition-cause preservation and release of the original response.

The producer finalizer retires its cancellation query/local signal, hook adapters, default pricing callback and supplied dependencies. Caller-owned signals and original hooks remain borrowed. The [baseline integration record](runtime-validation/2026-09-21-provider-core.json) contains 216 plain/audited executions on native one/four threads and Bun through real preparation, HTTP acquisition/retry and session processing. Prepared payloads and stream traces are compared against pinned pi source.

A further [72-execution integration record](runtime-validation/2026-09-21-provider-core-grammar.json) verifies non-default grammar properties after numeric/null payload replacement, exact tool-event order against the pinned processor, and original-callback usability after complete provider disposal on success and failures. Audited counters finish at zero. An independent missing-map reference control shows that the asserted argument key detects metadata loss; it is not a compiled production mutation.

`openai-responses-preparation-error.format` renders each preparation-error variant, preserving credential and constrained-sampling diagnostics. Native JSON errors use cause-specific Bend wording. `provider-request-error.render` preserves primary hook diagnostics when cleanup also fails and delegates retry failures to the existing retry formatter. Their generic laws are included in the full proof gate. Complete provider rendering still needs to compose them with transport and stream diagnostics; these formatters are not yet installed in the integration fixture.

[Native dependency ownership](openai-cleartext-runtime.md) is implemented separately: the cleartext runtime owns resolver/fetch/retry resources, the default owner adds native HTTP-date parsing, and the system owner retains loaded resolver/hosts diagnostics. The default owner passes [48 plain/audited native/Bun executions](runtime-validation/2026-09-21-cleartext-default-runtime.json); system loading passes [117 audited executions](runtime-validation/2026-09-21-system-settings.json). Full system-owner creation and owned acquisition now pass [90 plain/audited native/Bun executions](runtime-validation/2026-09-21-owned-acquire.json). Provider-session assembly has separate validation in progress. Initialization-failure injections at the default owner boundary do not simulate OS entropy failure inside lower-level creation.

The [completed root gate](proof-validation/2026-09-21-owned-provider.json) checks 502 public laws and 74 supporting lemmas and rejects 268 well-typed mutations. Its twenty-one existing unsafe declarations produce thirty-four concrete annotations; the existing file-fold driver newly enters this root. Default/system-owner, generic lazy-owner and payload-plan laws are included. No new unsafe declaration was introduced.

The complete public provider still requires transport selection/ownership, default SSE hooks, complete error rendering, the default clock at the stream boundary, native TLS and authentication lifecycle. The generic custom-fetch option also needs its actual injectable transport interface installed. No upstream suite is promoted by this assembly alone, and this milestone does not establish the full pi port.
