# pi-agent library port

Reference: pi-mono `46c9de402`, `packages/agent`. This is a partial library port, separate from the bootstrap CLI. The native loop is assembled, while the higher-level `Agent` API and its broader upstream suite remain pending.

`src/types.bend` preserves the typed tool, message, event, context, configuration and hook interfaces. Ordinary records and message/tool lists are immutable values. Custom messages and argument/result types are explicit generic parameters. Reusable callbacks, cancellation and running-agent state are effectful resources; they are not hidden inside ordinary data to reproduce JavaScript aliasing.

`toTool` projects an executable tool to its declaration without invoking callbacks. Argument preparation returns an original or replaced call, preserving metadata while allowing different raw/prepared argument types. Before-tool hooks return `BeforeToolCallUpdate` with explicit arguments, context and an optional decision. This preserves the ability to change execution arguments without revalidation. The public loop threads that update into prepared execution.

`src/agent-loop.bend` supplies the loop helpers: tool selection and execution policy, argument preparation, result merging/projection, after-tool hook finalization, awaited event emission, truncated-call failures, completion handling, queue polling, stop/next-turn hooks, context conversion, API-key resolution and injected assistant request/stream consumption. Pure transformations return updated values. The running request owns a synchronized context cell; emitted messages are immutable snapshots. Listener and hook failures use typed `Result` values and short-circuit subsequent work.

After-tool overrides use `Maybe`: absent fields retain their old values, while supplied fields replace them. Next-turn updates return context/messages/model/thinking changes explicitly. Costs, tool details, headers and configurations require no object disposal. Callback handles and running synchronization resources still require explicit lifetime management.

Run `sh tests/native-agent.sh` for request sequencing, retained event snapshots, queue/hook transitions, typed preparation, awaited emission, truncated failures and completion paths on one and four threads. Supplemental upstream-source comparisons remain in `tool_batch_vectors.py`, `tool_selection_vectors.py`, `before_tool_decision_vectors.py`, `turn_update_vectors.py`, `tool_result_vectors.py` and `failed_turn_vectors.py`. Type/interface checks are in `agent_types.py`, `loop_config_types.py`, `tool_preparation_types.py` and `tool_result_message.py`.

See [native Bend decisions](../../docs/native-bend.md) for approved behavior changes and retired compatibility fixtures. Named loop coverage is recorded in `tests/upstream-inventory.json`. It does not establish complete `Agent` API, extension runtime, schema-validator or provider parity.


`finalizeExecutedToolCall` now awaits the configured after-tool hook, supplies the original call and validated arguments, applies optional overrides and turns hook errors into error tool results. Generic embeddings provide an empty details value and a pure error renderer; JSON-detail embeddings use an empty native dictionary. Nine native cases verify successful/error executions, absent hooks/returns, termination overrides, error conversion and exactly-once invocation. Channel gates verify that asynchronous hooks settle before finalization returns, without timing assumptions.

`createAgentStream` now specializes the generic stream for agent events and final message histories. Agent-end settles the history independently of buffered event consumption; late pushes are ignored. `disposeAgentStream` releases its owned predicate/extractor callbacks after iterator users retire. The asynchronous public wrappers are implemented in `loop-stream.bend`.


`src/tool-update-scope.bend` tracks accepted updates for one tool invocation. Affine tickets prevent double completion, closing rejects late updates, and the result can fail before outstanding listeners drain. Resource disposal waits for that separate drain and requires the owner to retire retained callback aliases. Before closing, failures already available are selected in registration order; after closing, the first arriving failure wins. This matches the pinned execution helper's awaited update batch. `tests/tool_update_scope.py` checks the original helper's selection/rejection behavior, native scope transitions, independent invocations, 256 concurrent completions and compiler rejection of ticket copying. The scope is integrated with prepared tool execution and update forwarding; these are supplemental checks, not full agent-suite ports.


`executePreparedToolCall` now invokes the configured executor with validated arguments, the signal and its invocation update callback. It closes update admission immediately after execution settles, awaits accepted deliveries, preserves successful results and formats tool failures as error results. Listener failures propagate separately, including when the tool also fails. A fresh `ToolUpdateRun` supplies the invocation's update resources; the caller keeps that owner alive until retained callback aliases retire, then disposes it after outstanding deliveries drain.

`event-emission.bend` distinguishes ordered delivery initiation from completion. Starting emitters return a ready result or an affine pending delivery; the latter can finish concurrently with other listeners. `createAgentStreamEmitter` connects this protocol to the canonical stream. `createAwaitedEventSink` adapts it to existing lifecycle helpers that await delivery. Eight gated execution scenarios and a composed execution/finalization/result-stream test run on one/four threads in `tests/native-agent.sh`. These lifecycle components are integrated into the public loop. Full schema validation and broader upstream agent suites remain unfinished.


`prepareToolCallWith` composes first-match lookup, optional argument adaptation, required validation, before-hook updates and post-hook cancellation/blocking. Both raw and adapted calls go through the supplied validator; there is no successful-validation fallback. Typed adapter/validator/hook failures become immediate tool error results. Explicit context updates survive blocking and cancellation, and hook-updated arguments reach execution without revalidation. The required validation callback is an injection boundary while the full canonical schema validator remains pending. Twelve native pipeline cases supplement the named public-loop tests. The public fixtures inject actual native plain-schema validation; the full builder/reference vocabulary remains incomplete.

`tool-batch-parallel.bend` now composes the canonical lifecycle with ordered preparation and concurrent tool execution. Start events and immediate end events happen during preparation; prepared tools recheck cancellation before running. Successful batches deliver result messages in call order after all execution-end events settle. `start` returns an owned run, `result` performs one ordered delivery, and `dispose` drains workers before retiring their callback. On listener failure, callers retain the run and captured resources while sibling tools finish. Tool-update owners remain separate until retained callback aliases retire. Component and public-loop tests cover this behavior, including gated overlap, ordered results and sequential overrides.

`tool-execution.bend` now exposes the common `executeToolCalls` entry point over sequential and parallel lifecycle implementations. It selects mode once from assistant tool calls and the original context/config, preserving first-match lookup and whole-batch sequential overrides. Its owned `Execution` distinguishes a settled result from a concurrent run; callers consume `result` once and `dispose` before retiring captured resources. The native main loop owns these executions through result settlement and resource draining.

`turn-completion.bend` commits successful batch results to both histories, emits `turn_end`, and passes the completed immutable snapshot to stop/next-turn decisions. It preserves steering precedence and polls follow-ups only when neither tools nor steering requires another turn. `Continue` carries pending messages separately from committed history; `Finished` follows a settled `agent_end`. Batch/listener/hook failures propagate without later polls or events. The main loop connects this decision to the next request/preparation cycle.

`tool-changes.bend` now reconciles executable tools with transcript declarations while respecting the last pending system message’s intent. `turn-preparation.bend` combines that reconciliation with hook-returned context/model/thinking updates, conditional steering repolling and ordered turn/message events. Prepared and queued messages commit to both histories only after their message-end event succeeds. The returned `RequestState` is ready for the existing provider-request pipeline; `main-loop.bend` drives this state through the next request.


`main-loop.bend` assembles requests, assistant streams, tool execution, turn completion and preparation. `loop-entry.bend` implements `runAgentLoop` and `runAgentLoopContinue`, including continuation validation and initial declaration/prompt events. `stream-fn.bend` supplies a host-owned default-provider registry, resolving the selected provider at loop entry. `loop-stream.bend` launches `agentLoop`/`agentLoopContinue` asynchronously and exposes immutable events and a repeatable typed result. Invalid continuation is rejected before launch; failures close iteration with a typed error and no synthetic `agent_end`, as approved by the user.

A wrapper run owns its worker, stream callbacks, tool-update owners and batch executions. Retire iterator/result observers and retained tool-update aliases before disposal; `dispose` joins the worker and drains batches before releasing callbacks. Provider/configuration/validator callbacks remain borrowed until disposal completes. The generic stream publishes terminal state and event ownership atomically, with gated race regressions.


All 24 named cases from the pinned `packages/agent/test/agent-loop.test.ts` are ported across `test/agent-loop*.bend` and pass on one/four threads after fresh builds. The inventory records this suite as ported. This is a test-suite milestone, not completion of the package: `Agent` orchestration, broader agent tests, full schema integration and provider implementations remain pending. See [upstream coverage](../../tests/UPSTREAM.md) for the assertion mapping and native adaptations.


`agent-state.bend` now implements immutable `AgentState` initialization, default model/conversion, transcript-derived `systemPrompt`, run start/finish transitions and event reduction. A native string set tracks pending tool IDs. `agent_end` clears the partial message but preserves the active flag and pending IDs until `finishRun`, so the future owner can await final listeners before becoming idle. `tests/agent_state_check.py` compares 161 snapshots with the pinned constructor/reducer/lifecycle helpers on one/four threads, with additional default-model and retained-snapshot checks. This is a state component; public subscriptions and prompt/continue execution remain pending and no `agent.test.ts` cases are promoted yet.

`pending-message-queue.bend` and `agent-queues.bend` implement immutable FIFO steering/follow-up queues with all-at-once and one-at-a-time modes. `agent-continuation.bend` returns a typed decision and updated queues: busy/empty-history rejection, ordinary continuation, or queued prompt selection with steering priority and the initial-poll skip flag. The future Agent owner must commit that decision and claim the run atomically. `tests/agent_queues_check.py` compares 1,754 queue snapshots and 1,024 continuation decisions with the pinned source on one/four threads, plus native pair-isolation and retained-snapshot checks. Its oracle intercepts the selected run entry; it does not test native prompt execution, skip-flag consumption or public Agent integration. No upstream suite is promoted by these component checks.

`agent-lifecycle.bend` supplies synchronized run ownership over a typed immutable state value, intended to hold Agent state and queues together. Pure preparation and run claiming are atomic; failed or competing claims preserve the state. Cancellation reaches the active signal without declaring idle. `runWithLifecycle` awaits execution and optional failure recovery, then commits the finish reduction and settles waiters even when recovery returns an error. Completed run/signal handles remain borrowed and inspectable until owner disposal; the owner must drain observers and retire aliases before disposing. Native tests cover 64 competing-start/restart sequences and six execution/recovery paths on one/four threads. This internal component is not yet wired to public Agent options, event subscriptions, failure-message construction or prompt/continue execution; `agent.test.ts` remains pending.

`agent-runtime.bend` now composes the real Agent state, both queues and lifecycle owner in one synchronized cell. Prompt/continue preparation commits with the run claim; concurrent continuation cannot consume a second steering batch. Reset checks active-run status in the same transaction, replays the current system-message baseline, clears queues/runtime fields and retains model, thinking level and executable tools. Event reduction commits before returning the active handle for future listener dispatch; even the upstream idle-event error preserves its prior state reduction. `tests/agent_runtime_check.py` compares 588 snapshots with actual pinned Agent methods using a gated executor, across three histories and both queue modes. Native tests additionally exercise 64 simultaneous continuation races. These pass on one/four threads, as do 161 state comparisons (now including reset) and lifecycle regressions. Provider/loop invocation, listener dispatch, public Agent options and failure-message construction are still unwired; run preparation is not a finished public prompt/continue API.
