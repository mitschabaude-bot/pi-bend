# Agent library port

`src/types.bend` starts the canonical port of pi-mono’s agent tool interfaces. `AgentToolResult` retains text/image content, typed details, usage and optional termination. `AgentTool` retains every upstream field: inherited declaration fields, label, argument preparation, execution, replay policy and execution-mode override. Preparation/execution/update callbacks use the runtime’s reusable callback handles. Execution receives a typed record containing the four original arguments; recoverable failures use `Result` rather than host exceptions.

`toTool` is the explicit Bend projection from an executable tool to its base `ai.Tool` interface. It retains schema and sampling values and removes executable/display-only fields without invoking callbacks. The transcript library subsequently performs its normal schema snapshot. This models the structural upcast TypeScript performs implicitly; it is not a separate approximate declaration serializer.

This module remains partial. Schema and validated argument types are independent parameters until the TypeBox `Static<Parameters>` relationship is implemented. Raw arguments, abort-signal handles and thrown errors are caller-typed pending their runtime adapters. Scoped updates, execution lifecycle, preparation/validation, replay enforcement and execution scheduling are not implemented by these type declarations. Agent state accessors, complete loop behavior and the agent implementation remain pending.

The upstream replay-suite declaration-comparison test uses a real typed executable tool, including preparation and execution callbacks. It checks all three original equality assertions and additionally verifies that declaration projection invokes neither callback. Canonical sources remain pure Bend. The ai/agent dependency graph currently requires the [shared-import compiler fix](../../patches/README.md).

`AgentMessage` now includes canonical pi-ai messages plus a caller-defined custom-message union, adapting TypeScript declaration merging to an explicit Bend type parameter. Both preserve shared object handles. `AgentToolCall` aliases the existing shared pi-ai tool-call type. Agent `ThinkingLevel` aliases the model-level union that includes off, and `QueueMode` retains all/one-at-a-time variants.

`AgentEvent` includes all ten upstream variants with their original payload fields. `eventType` returns their literal source discriminators; Bend constructor names replace the reserved `type` field. Assistant message updates carry the canonical `AssistantMessageEvent`, retaining the same live assistant object. Partial and final tool payloads have independent type parameters corresponding to the source's `any` fields; no generic JSON conversion occurs. `BeforeToolCallResult` and `AfterToolCallResult` preserve every optional field, including absence versus false/empty values. These are declarations, not implementations of hook merging, event ordering, array mutation semantics or subscription settlement.

`python3 tests/agent_types.py` checks ten event field sets and both hook result field/optionality sets directly against the pinned upstream file. Native one/four-thread tests construct every event variant, verify payloads and retained assistant/custom-message identity, and compilation rejects incompatible partial/final tool payloads. These supplemental type checks do not mark any upstream behavior suite complete.

`src/agent-loop.bend` now starts the loop's internal outcome handling with the upstream `ExecutedToolCallOutcome` and `FinalizedToolCallOutcome` records. `applyAfterToolCallResult` extracts the merge portion of `finalizeExecutedToolCall`: no hook return preserves the original result reference, while a supplied override allocates a new result even when every field is omitted. Content replaces the whole list; empty content, false error/termination flags, zero and empty-string details remain meaningful replacements. Omitted fields and nullish details keep the original values. Shared details and nested usage-cost references are retained, and the original result is not mutated. The caller supplies a pure nullish classifier for the opaque details type; this is an explicit typed boundary pending integration with the complete dynamic-value runtime.

`python3 tests/tool_result_vectors.py` extracts and executes the actual merge expression from the pinned upstream source as a test oracle, then compares 108 cases on one/four native threads. Tests cover absent-return identity, new-result allocation, unchanged original content, independent override fields, falsy/nullish details and shared reference preservation. Hook invocation, thrown-error handling, arbitrary extra own properties/getters, full array/object mutation behavior and event emission are not implemented by this helper. The low-level agent loop remains unfinished; these comparisons do not complete its upstream suite.

The loop's execution-policy helpers now preserve upstream whole-batch selection: one called tool with a sequential override makes the entire batch sequential; otherwise a sequential global setting applies, with parallel as the default. Definition lookup uses the first matching name, including when that definition has no override. It reads shared tool and tool-call objects and never executes tools. The per-tool scan still happens before the global setting is checked, matching upstream evaluation order. Inputs are the already-filtered tool-call list; assistant-content filtering and execution scheduling remain separate unfinished loop steps.

`shouldTerminateToolBatch` requires a nonempty batch and strict true termination hints on every finalized result. Missing/false hints stop the scan, and the error flag does not independently prevent termination. `python3 tests/tool_batch_vectors.py` runs 126 execution-mode cases and all 121 ternary termination sequences of lengths zero through four against extracted upstream expressions, on one/four threads. Native checks verify subsequent mutations of tool definitions, call names and finalized results are observed without invoking execution callbacks. These tests establish policy selection, not parallel start/completion ordering, abort scheduling or completion of the upstream agent-loop suite.

`AgentEventSink` now preserves the loop's exported event callback contract as a reusable typed IO callback. Its recoverable `Result` explicitly adapts rejected/thrown listener errors. `emitToolExecutionEnd` emits the finalized result by shared identity with its current tool-call id/name and error flag. `emitToolResultMessage` awaits `message_start` before emitting `message_end`, passes the same tool-result message to both, propagates failures unchanged and omits the end event if the start listener fails. No timestamps or replacement message objects are introduced by emission.

`python3 tests/tool_emit_vectors.py` runs the actual two upstream helper bodies as an oracle for five success/failure traces. Native tests on one/four threads suspend listeners behind explicit deferred gates, verify the emitter remains pending, and check that later events observe listener mutations to the original object. Execution-result mutation is retained even when its listener fails. These checks establish awaited dependency order, not JavaScript microtask scheduling or full `Agent.subscribe()` settlement. Tool-result construction, the complete execution pipeline and the main agent loop remain pending.

`createToolResultMessage` now projects a finalized typed result into a fresh shared pi-ai tool-result message and reads the current Unix wall-clock timestamp. It preserves tool-call id/name, content, details, optional usage and the finalized error flag; the termination hint stays internal to batch policy. Details and usage-cost references remain shared and caller-owned. `toolResultMessageAt` is the pure field projection. `python3 tests/tool_result_message.py` checks fields, fresh message identity, live timestamp bounds, retained shared mutation and payload ownership on one/four threads. Dynamic null/absent content normalization and full mutable-array/extra-property semantics still require the dynamic-value boundary; the canonical typed result already requires content.

`prepareToolCallArguments` now invokes the optional argument adapter once and preserves the original call handle when no adapter exists or when its returned arguments strictly equal the call's current arguments. The comparison occurs after the callback; replacement id/name/signature/namespace fields are also read from the current call. A different argument value allocates a new call, and recoverable adapter failures preserve their original error payload. Tools are not executed during preparation.

`PreparedToolCallArguments<RawArguments, Arguments>` is an explicit Bend adaptation: its original/replaced variants retain differently typed shared handles without unsafe casts. Neither variant implies schema validation. A typed strict-equality function supplies the opaque argument comparison, pending the complete dynamic-value adapter. `python3 tests/tool_prepare_vectors.py` checks six cases against the actual upstream helper body on one/four threads, covering absence, shared versus equal-but-distinct arguments, callback mutations, copied metadata and failure identity. An additional native test uses different raw/output types. Dynamic extra own properties/getters, callback receiver semantics, exact synchronous/Promise scheduling, TypeBox validation and the full preparation/execution pipeline remain pending.

The canonical context contracts now include `AgentContext`, `BeforeToolCallContext`, `AfterToolCallContext`, `ShouldStopAfterTurnContext`, its `PrepareNextTurnContext` alias, and `AgentLoopTurnUpdate`. Raw provider arguments and schema-validated arguments remain separate type parameters. Hook records preserve shared assistant, tool-call, executed-result and agent-context handles. Next-turn updates retain optional replacement context/messages/model/thinking fields, including an explicit off thinking level.

`AgentMessageArray` and `AgentToolArray` represent array identity using shared dense-list cells, separately from their shared element objects. The agent-end message array and turn-end result array now use the same ownership model; retained events can observe updates. This does not yet provide JavaScript sparse-array/index/property APIs. `copyContextMessages` implements the typed portion of run initialization: it allocates a new context and message-array cell, appends initial messages in source order, and retains existing message objects and the optional tools array. Callers own the new context/array cells; their elements and supplied tools remain caller-owned. Arbitrary extra context properties and getters remain outside the current typed record.

The type runner now checks seven context/hook record field sets plus all ten event variants against the pinned source. Native one/four-thread tests verify copied-array independence, shared elements/tools/events, raw-versus-validated arguments, hook/result/context identity, next-turn replacement fields and ownership. Compilation rejects treating validated U32 arguments as raw strings. State accessor behavior, full array semantics, complete loop configuration, hook invocation and provider-loop integration remain unfinished; no upstream behavior suite is marked complete by these declarations.

`AgentLoopConfig` now retains all 34 fields from its complete upstream inheritance chain, including model/conversion requirements, provider options, context transforms, key resolution, steering/follow-up queues, turn decisions/preparation and tool hooks. Callback input records preserve the original argument groupings; shared context/message arrays remain shared. Recoverable callback errors use `Result`; invocation must still honor each callback's documented fallback or interruption policy. `toSimpleStreamOptions` projects the provider-visible fields without defaults, callback invocation or cloning.

The agent `StreamFn` uses canonical model, normalized transcript and optional simple-stream options, returning the canonical assistant event stream through IO. Its signature has no out-of-band request-error result, matching the source contract that request failures belong in stream events. This type contract does not guarantee provider behavior or emulate Promise microtasks. Fetch, telemetry and signal runtime types remain pending integration as documented for provider options.

`python3 tests/loop_config_types.py` compares all inherited fields/optionality with upstream and runs native one/four-thread identity/non-invocation checks. Negative compilation rejects unnormalized context and a stream function returning a separate error result. Existing message/context/hook tests remain passing. State accessors, callback invocation policies, provider calls and complete agent-loop execution remain unfinished; no upstream behavior suite is completed by these declarations.

`applyTurnUpdate` now implements the typed next-turn replacement block from `runLoop`. An absent update retains the configuration and context references and allocates an empty prepared-message array. Any supplied update object creates a new shallow configuration, even when empty; optional context/model replacements retain their supplied identities. A supplied message array is reused, including an empty one. Omitted thinking preserves provider reasoning, off removes it, and all other levels replace it. Unrelated configuration fields and callbacks are retained without invocation, and the original configuration remains unchanged.

`PreparedTurnState` is the internal result of this extracted block. Newly allocated configuration/message-array cells are caller-owned; supplied models, contexts, message arrays and callbacks keep their owners. `python3 tests/turn_update_vectors.py` compares 195 combinations against the actual pinned source block on one/four threads, including absence versus an empty update, every thinking level, replacements, shared identity and original-state preservation. Hook invocation, steering polling, event emission, dynamic extra properties/getters and complete turn orchestration remain unfinished; these tests do not complete the agent-loop suite.

`prepareNextTurn` now invokes the optional configuration callback with the original completed-turn context, awaits its settlement, then applies its update. Callback-side configuration mutations remain visible: a supplied update copies the configuration after the callback, while an absent return retains its identity. Recoverable callback failures propagate unchanged without applying replacements, retaining mutations the callback already made. The helper belongs after a completed turn; it does not decide when another turn should run.

`python3 tests/prepare_turn_vectors.py` compares five cases with the actual pinned preparation/update block: no callback, absent return, empty update, message/thinking replacement and rejection. Native one/four-thread tests hold callbacks behind explicit gates, check pending settlement, exact context/configuration/message identities, callback counts and retained mutations. Steering polls, turn-start events, callback receiver semantics, global Promise scheduling, dynamic properties and complete loop orchestration remain pending. These supplemental comparisons do not complete an upstream suite.

`pollSteeringMessages` and `pollFollowUpMessages` now select and await their current configuration callbacks. Returned message arrays retain their identities; an absent callback allocates a fresh empty array, and recoverable failures propagate unchanged. `repollSteeringMessages` reads the pending array's live contents first and skips polling when it already contains a message. This preserves upstream's one-at-a-time delivery guard after preparation. Newly allocated empty arrays belong to the caller; supplied arrays retain their original owners. The callback contracts require arrays, matching the source types; dynamically returning null or another non-array value is outside these typed helpers.

`python3 tests/queue_poll_vectors.py` compares 24 cases against the actual upstream poll statements and repoll guard. A returned array is mutated while its callback is suspended to check live shared contents. The opposite queue must never be invoked. Queue storage, preparation-to-poll-to-event integration, complete turn orchestration and global Promise scheduling remain unfinished; no upstream suite status changes.

`shouldStopAfterTurn` now awaits the optional stop hook with the shared completed-turn context; absence means false, and recoverable failures remain failures. `finishCompletedTurn` connects that decision to the following source block: true awaits `agent_end` without polling, false polls the current steering callback, and a hook failure does neither. A callback may replace configuration fields before polling. The end event retains the original local new-message array even if the hook replaces `completed.newMessages`. This helper runs after `turn_end` and completed-context construction, which remain responsibilities of the unfinished main loop.

Its internal result uses `Done(None)` for a settled stop and `Done(Some(messages))` for continuation with the exact pending array; errors propagate unchanged. The helper does not own the completed context, callback handles or supplied arrays. An absent steering callback allocates an empty array owned by the caller. `python3 tests/stop_turn_vectors.py` compares six original-source traces covering absence, false/true decisions and hook/event/queue failures. Native one/four-thread checks independently gate the hook and subsequent event or queue callback, verify callback replacement, preserve context mutations on failure, and check end-event array identity. Full turn execution, follow-up orchestration, dynamic truthiness/receiver behavior and global Promise scheduling remain pending; no upstream suite is newly complete.

`convertContextMessages` now implements the transform/conversion prefix of `streamAssistantResponse`. It captures the context's message-array reference, optionally awaits `transformContext(messages, signal)`, then reads and awaits the current `convertToLlm` callback. A transform may replace that callback before conversion; replacing `context.messages` does not override the transform's explicit return value or the originally captured array. Missing transformation preserves the original array. Both recoverable failures propagate unchanged, and a transform failure skips conversion. Input and returned arrays remain shared and caller-owned.
